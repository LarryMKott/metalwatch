## CI/CD 分平台流水线落地（2026-09-26，提交 6d5cfb6）

### 最重要的发现：既有 CI 从未跑通过

推完后查 Actions 运行历史（GitHub REST API），发现 **`main` 与 `dev` 的每一次推送都是 failure**，
失败步骤固定是「竞态检测（本机不可用，CI 必跑）」：

```
[!! failure] 后端（vet / race / cover / build）
    失败步骤: 竞态检测（本机不可用，CI 必跑） -> failure
```

根因：旧 `ci.yml` 全局 `env: CGO_ENABLED: 0`，而 race 检测器**依赖 cgo** →
`go test -race` 直接报 `-race requires cgo; enable cgo by setting CGO_ENABLED=1`
（本机已实测复现）。**「写进 workflow」不等于「跑通过」——以后接手任何 CI 先查运行历史。**

### 交付内容

**`ci.yml`（重写为 8 个 job）**：后端质量门禁（fmt / vet / **race** / 覆盖率）、

**`release.yml`（新增，7 个 job）**：tag `v*` 或手动触发 →

## CI 首个失败 job 定位：WS 订阅登记晚于握手（2026-09-26，D38）

**现象**：`6d5cfb6` 的 run `36220229840`，13 个 job 只挂 1 个 —— `后端 · 质量门禁` 的

FAIL	github.com/LarryMKott/metalwatch/api/web	6.674s

### 排查方法论（下次直接照做）

1. **先定性偶发 vs 必现，再查方向**。本机复现不出（`GOMAXPROCS=1 -cpu=1` 单进程
   `-count=20` 全绿；CI 同款 `-coverpkg=./...` 也通过），于是用 GitHub API
   **重跑失败 job** → 同一 commit **13/13 全绿** → 判偶发 → 往**时序**查，别折腾环境。
2. 拿权威日志要用 `D:/pj/.spikes/tools/ci_act.py`（`dump` 落盘全部 job 日志 /
   `rerun` 重跑失败 job / `wait` 轮询结论）。**run 的 jobs 列表里没有 `logs_url`**；
   日志接口 302 到 Azure 签名 URL，**自动跟随会把 GitHub 令牌漏给 Blob → 401**，
   必须 `NoRedirect` + 手动取 Location 匿名下载；返回体是**带 BOM 的纯文本**不是 zip。

### 根因与修复

`internal/ws/hub.go` 的 `serve` 里 `upgrader.Upgrade`（握手完成、客户端已收 101）
在 `h.subscribe()` **之前**。客户端一收到 101 就认为订阅生效并立即上报，
服务端此刻还没把它放进 `clients`；而 `BroadcastJSON` 对空订阅集**不报错只丢帧**
（既定语义），窗口内的推送被静默吞掉 → 订阅者等读超时。

- **量化**：真实 HTTP 升级路径写 300 轮实验（Dial 返回即广播、不睡眠）→ 旧顺序
  **丢 49/300（16%）**；改成先 subscribe 后 Upgrade → 200 轮全过。
- **回归测试**：`internal/ws/hub_test.go::TestServeRegistersSubscriberBeforeHandshake`
  （任一轮丢失即 fail-fast）。把顺序临时倒回去验证 → **第 1 轮**即失败，
  报错与 CI 同型。**改产品代码前先确认测试能抓住旧行为**，否则守的是空气。
- **e2e 可诊断性**：连上后先断言 `hub.ClientCount() == 1`，读超时信息带订阅数，
  把「订阅没登记」与「告警没触发」分开 —— 否则两者都表现为同一个 5s 超时。
- **验证**：backend 全量 18 包 `go test -count=1` 全绿；gofmt/vet 干净。

### 结论性经验

## Agent 会话的两个并发缺陷（D41，2026-09-26）

**触发**：CI run `36223226787`（提交 `cc27bcb`，**只改了一个 markdown**）失败在
Agent 测试：`session_test.go:193: 等待超时: spool 清空`；重跑该 job → 13/13 绿；
本机 `-count=300` 与 `-cpu=1 -count=60` 全绿。

**注意**：本地既然调度不出来，**就不要再靠运气复现，去读代码**。这两个缺陷本地
永远复现不出来（都是抢占窗口），但读一遍就看出来了。

**两个缺陷**（`agent/internal/grpcstream/session.go`，行号为修复前）：

1. **并发写同一条 gRPC 流**：`serveSession` 先发布 `s.st`（131-133）**再**调
   `replay`（141），而 `replay` 里是裸 `st.Send`（192）**不持 `s.mu`**；
   `trySend`（249）持锁后也调 `s.st.Send`。gRPC 不允许跨 goroutine 并发 `SendMsg`。
   窗口 = 整个 replay 时长，**积压越大越宽**。结构体注释（63-65 行）本来就写着
   「Send 全部经互斥锁串行化」—— **代码违反了自己写下的规格**，这类地方信号最强。
2. **落盘残留 → 延迟无上界**：spool 只在 replay 里排空一次；`collectOnce` 若在
   「读 `s.st` 为 nil」与「真正落盘」之间被抢占，落盘会落在 replay 最后一次 `Peek`
   之后，此后**整个会话没人再排空它**，要等下次重连。

**修法**：`replay` → `drain(ctx) error`（每批持 `s.mu`），`collectOnce` 每轮开头先 `drain`。

**⚠️ 一个被自己否掉的更直觉写法**：「落盘后立刻再排空」**堵不住** —— 残留若是等到
下一轮 `trySend` 成功时才遇到采集周期，`trySend` 成功会提前 `return`，残留照样躺着。
**正确的不变式是「每个采集周期都排空」，不是「每次落盘后排空」。**

### 方法论（可复用）

- **偶发 ≠ 缺陷随机，往往只是观测粒度太粗。** 同一个机制，CI 上要等负载帮忙才偶发，
  本机 0%；把观测点从「整个会话生命周期」换成「一个采集周期」后 **100% 必现**
  （守卫测试在旧代码上 2.22s 确定性失败）。**先找一个能把窗口钉死的粒度，再写守卫。**
- **读 Actions 日志要区分「回显的脚本」与「脚本的输出」**：这次日志里有
  `echo "::error::以下文件未格式化："`，是 runner 回显 gofmt 步骤的**源码**，
  不是失败信号（证据：后面 `go vet`/`go test` 都照跑了）。差点被它带偏。
- **对端异步时，断言前必须先同步**：守卫测试第一版在 `collectOnce` 返回后立刻断言
  服务端收到的批次，得到 `实际 1 条: [backlog-1]` —— 实时那条其实发出去了，
  只是 fake 服务端异步 `Recv` 还没读到。改成先 `waitFor(reportCount >= 2)`。

**顺带**：CI 的 Agent 测试加了 `-race`（本机无 gcc 跑不了）。边界说清：race 抓的是内存竞态，
gRPC 的「并发 SendMsg」是协议层约定，`-race` **未必**报得出来 —— 别把它当成这条不变式的证明。

### 同一类毛病在 Makefile 上又出现一次（检查项自己抹掉信号）

而 `fmt` 是 `gofmt -s -w` —— **先把不合格的地方改写掉，再让后面的步骤判通过**。
