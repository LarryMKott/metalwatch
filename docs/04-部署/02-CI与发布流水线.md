# 02 · CI 与发布流水线

> 两条 GitHub Actions 流水线，职责严格分开：
> **`ci.yml` 只做测试与编译验证**（不产出任何可发布物），
> **`release.yml` 才出包**（按 tag 触发，产物进 GitHub Release）。

## 1. 触发条件

| 流水线 | 触发 | 说明 |
| --- | --- | --- |
| `CI` | `push` 到 `main` / `dev`、`PR` 到 `main`、手动 | 同一 ref 的旧运行会被取消（`concurrency`） |
| `Release` | 推 `v*` tag、手动指定版本号 | 手动触发时以 HEAD 为准，tag 不存在则由 `gh release create` 创建 |

```bash
# 标准发版流程
git tag v0.2.0 && git push origin v0.2.0
```

推 tag 前建议先本机自查一遍（见 §6）。

## 2. CI：分平台的测试与编译

| Job | 平台/矩阵 | 做什么 |
| --- | --- | --- |
| `backend-quality` | 宿主机 | `gofmt -s -l`、`go vet`、**`go test -race -count=1`**、覆盖率 |
| `backend-build` | `linux/amd64`、`linux/arm64`、`windows/amd64` | 按目标平台 `go vet` + `CGO_ENABLED=0` 静态编译 |
| `agent-test` | 宿主机 | `gofmt`、`go vet`、`go test -count=1` |
| `agent-build` | `linux/amd64`、`linux/arm64`、`windows/amd64` | 按目标平台 `go vet` + 编译（入口 `cmd/<goos>`） |
| `frontend` | Node `22.22`、`24.21` | `npm ci` → `type-check` → `build`（双版本兼容是 `engines` 的承诺） |
| `fpk-skeleton` | — | `check_fpk.py`（强制文件 / JSON / LF / 端口一致 / native 形态 / platform 断言） |
| `python-lint` | — | `ruff check tests/python`（**范围见 §5 说明**） |
| `python-tests` | — | 编译并真实拉起服务端 → `run_tests.py all --fast`（冒烟/单元/集成 + 端点覆盖率） |

### 两个必须知道的坑（已在配置里修掉）

1. **`CGO_ENABLED` 不能全局设 0。** race 检测器依赖 cgo，全局设 0 会让
   `go test -race` 直接报 `-race requires cgo`——那条步骤等于永远失败。
   所以本仓库把它按**步骤**作用域声明：编译步骤 `CGO_ENABLED=0`，race 步骤 `CGO_ENABLED=1`。
2. **`-count=1` 不能省。** 默认命中测试缓存会输出 `ok ... (cached)`，
   把真实的编译/逻辑失败掩盖过去（本机踩过一次：全量测试"全绿"，实际有包编译失败）。

### 为什么跨平台 `go vet` 也要按目标平台跑

`GOOS=windows go vet ./...` 能抓出「只在某个平台编译不过」的问题。本项目踩过一次：
把共用函数写进带 `//go:build linux` 的文件，Linux 全绿、Windows 构建 `undefined`。

## 3. Release：分平台出包

```
meta（解析并校验版本号）
  ├── webui          前端只构建一次 → webui-dist（tar.gz）
  ├── server ×3      linux/amd64 · linux/arm64 · windows/amd64
  ├── agent  ×3      linux/amd64 · linux/arm64 · windows/amd64
  └── fpk    ×2      x86（amd64）· arm（arm64）        ← 依赖 webui
        ↓
verify-server        拿「将要发布的那份二进制」跑 10 项真实冒烟
        ↓
release              归集 → 改名 → SHA256SUMS → GitHub Release
```

### 产物命名

| 类别 | 产物名 |
| --- | --- |
| 服务端 | `metalwatch-server-<os>-<arch>[.exe]` |
| Agent | `metalwatch-agent-<os>-<arch>[.exe]` |
| 飞牛包 | `metalwatch-fpk-x86_64-<版本>.fpk` / `metalwatch-fpk-arm64-<版本>.fpk` |
| WebUI | `metalwatch-webui-<版本>.tar.gz` |
| 校验和 | `SHA256SUMS`（格式与 `sha256sum -c` 兼容） |

**命名规则集中在 `deploy/tools/collect_release_assets.py`**，改 workflow 里的
`upload-artifact` 名必须同步改那里；两者不一致会在归集阶段报「缺产物」而失败，
不会静默发一个缺包的版本。

### 为什么 FPK 必须出两个包

包内含原生二进制，飞牛清单的 `platform` 只有 `x86` / `arm` 两个合法值
（写 `all` 会让 ARM 设备装到 x86 包然后启动失败，`check_fpk.py` 有断言）。
`build_fpk.py` 的 `--platform` 缺省按 `--goarch` 推导（`amd64→x86`、`arm64→arm`），
推导不出来时**直接报错**而不是回落到 x86——架构标错的包比不出包更危险。

### 发布前的那道冒烟

`verify-server` 下载 `server-linux-amd64` 产物，用
`smoke_server.py --binary <产物路径>` 直接跑，验证的是**将要交付的那个文件本身**，
不是「拿同一份源码再编译一次的结果」。两者未必等价：本机踩过 `-trimpath` 抹掉
GOROOT 后二进制缺时区数据、**启动即死**的坑，只有拿真产物跑才发现得了。

### fnpack 依赖

打包用飞牛官方 CLI，版本钉在 workflow 的 `FNPACK_VERSION`（现为 `1.2.3`），
从 `static2.fnnas.com` 下载。`build_fpk.py` 在 CI 里带 `--require-fnpack`：
**缺 fnpack 直接失败**，不允许「静默跳过打包却报成功」。

## 4. 手动发草稿

Actions → Release → Run workflow，填版本号并勾选 `draft`。
草稿会先建好 Release 与全部资产，人工确认后再手动 publish。

## 5. 已知边界（不要误以为流水线已经覆盖）

| 事项 | 现状 |
| --- | --- |
| **服务端尚未提供 WebUI 静态服务** | 后端没有任何 `go:embed` 前端产物、也没有静态路由；`NoRoute` 直接返回 404 JSON。因此**当前打出的 FPK 里 WebUI 不会生效**（桌面入口是指向 `:18080/` 的 iframe）。流水线如实打包了现有内容，这是功能缺口不是流水线问题 |
| `deploy/` 未纳入 ruff | `ruff check deploy` 仍有 21 条（多为 `BLE001` 盲兜底异常）。清干净再扩范围，别用 `--select` 把它"弄绿" |
| 真机三项验证 | 静态二进制可运行 / `package` 用户写权限 / 重装数据恢复 —— 本机无 fnOS，只能在真机做 |
| Windows Agent 的 C# NativeAOT 组件 | 本机无 .NET SDK 未编译；流水线只出 Go 侧 Agent |
| ARM 包未经真机验证 | 能编出来、`manifest.platform` 写对，但没在 ARM 飞牛设备上装过 |

## 6. 推 tag 之前本机自查

```bash
export GOPROXY=https://goproxy.cn,direct GOSUMDB=off

# 后端 / Agent
(cd backend && gofmt -s -l . && go vet ./... && go test -count=1 ./...)
(cd agent   && gofmt -s -l . && go vet ./... && go test -count=1 ./...)

# 关键平台的编译（-race 本机跑不了，进 CI）
(cd backend && CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -o /dev/null ./cmd/server)

# 骨架与打包链路
python deploy/tools/check_fpk.py
python deploy/script/build_fpk.py 0.0.0-check --skip-frontend   # 无 fnpack 时会明确告知跳过

# 冒烟（用真产物；本机 Windows 下用 Windows 产物跑同一套代码路径）
python deploy/tools/smoke_server.py --goos windows
```

workflow 文件本身的校验（YAML 解析 / matrix 键覆盖 / artifact 名交叉比对 /
`run` 块 shell 语法）目前用一次性脚本在仓库外完成，尚未入库。
