## 二、必须修正的 PRD 条目（D1–D8）

### D1 持久化要落到 `TRIM_PKGVAR`，而不是笼统的「飞牛持久存储」

PRD §2.7.2 说"挂载到飞牛持久存储"。实际唯一可靠方式是**全部读写都走 `TRIM_PKGVAR` 指向的持久卷**（native 形态下由进程直接读写，不经任何挂载编排）。
**注意卸载语义**：`uninstall` 时飞牛会清理应用目录，因此 `cmd/uninstall_init` 里必须先按用户选择做备份 + 条件删除（骨架已实现：默认保留，且无论如何先把 SQLite 元数据库复制到共享目录 —— 时序库可能数 GB，不做无条件复制）。

### D2 「日志输出到飞牛日志中心」在官方文档中**没有对应能力**

核对结果：官方文档只在 Docker/Native 案例里写「日志写本地文件」，环境变量清单里的 `TRIM_TEMP_LOGFILE` 仅用于**生命周期脚本向用户展示错误**，没有任何第三方 FPK 应用向飞牛日志中心投递日志的接口。
**降级方案（P0）**：日志写 `${TRIM_PKGVAR}/logs/`（jsonl，按天切分 + 大小轮转），WebUI 提供日志检索页。
**待验证（P2）**：尝试同时写 `/dev/log`（syslog）。是否被 fnOS 收集、能否在系统日志里检索，必须在真机上验证后再决定是否对外宣传该特性。

### D3 只有一个 `service_port`：WebUI 与 Agent 上报必须同端口分流

manifest 单端口是硬约束，且 `desktop_uidir` 入口的 `port` 必须与之相同，否则桌面图标点开是空白页。
- **P0 设计**：`service_port=18080`，进程直接监听该端口；`/` 与 `/api/v1/*` 给 WebUI/管理 API，`/api/v1/agent/*` 给 Agent 上报，`/metrics`（二期）对外导出。
- **PRD §5.4「FPK 配置内自定义 WebUI/API 端口」降级为 P2**：wizard 改端口不会同步到 manifest 与 ui/config，会导致入口打不开。要做得先验证飞牛网关是否支持端口重写，验证通过再开放。

### D4 「复用飞牛 OS RBAC 账号体系」缺依据

官方文档提供的是**出站**能力（`TRIM_API_TOKEN` 调用飞牛开放 API），没有「FPK 应用读取 fnOS 用户/角色并复用登录态」的说明。
- **P0**：应用自建 RBAC —— `admin / operator / viewer` 三角色 + 会话 Cookie/JWT，账号在安装向导里初始化。
- **P2 待验证**：若开放 API 能返回用户列表与角色，再考虑单点登录。

### D5 IPMI 采集不需要 root，但不能把 `run-as` 设成 root

IPMI 走网络（UDP/TCP 623），进程内即可完成，`config/privilege` 保持 `run-as: package`。
**唯一例外**是二期的「网段扫描」若采用原始套接字才需要提权 —— 届时改为「由用户显式开启的独立 helper」，不要整体提权。

### D6 「FPK 内限制 CPU/内存配额」~~要靠 compose 实现~~ → ⚠️ 已失效，见 D14

manifest 无资源配额字段。原方案用 compose 的 `cpus` / `mem_limit`。
**Native 化后无配额声明机制**，改为进程自限：`GOMEMLIMIT` + TSDB head 上限 + SQLite `cache_size`，目标常驻 ≤250MB。

### D7 双存储的选型 ~~（MySQL 与 SQLite 二选一）~~ → ⚠️ 已失效，见 D13

原结论是「MySQL 功能全但重（常驻 1.2GB 起），可评估换 SQLite」。
**Native 化后不再有二选一：直接落 SQLite（纯 Go 驱动）+ 进程内嵌时序存储**，见 D13。

### D8 GeoIP MMDB 的包体积与许可

- GeoLite2-City 解包后 60MB+，直接内嵌会让 `metalwatch.fpk` 膨胀到几十 MB，且 MaxMind 的再分发许可有约束。
- **P0 做法**：内置 Country + ASN（体积小、足以支撑「地域标签 + 筛选」），City 级精度通过共享目录 `metalwatch/geoip` 由用户自行放置并热加载（骨架已建目录）。
- **待办**：确认所选 MMDB 数据源的许可证文本，随包附 `LICENSE-geoip.txt`。隐私提醒：GeoIP 只用于**给资产打标签**，不采集访问者 IP。

## 三、PRD 未写、但必须补的设计（D9–D12）

### D9 BMC 密码加密的密钥从哪来（PRD 只写了「AES 加密」）

- 算法：AES-256-GCM，每条记录独立随机 nonce，**AAD 绑定 `host_id`**（防止密文在主机间搬运）。
- 密钥：首次安装随机生成 `master.key`（0600，存 `TRIM_PKGVAR/data/secret/`），与数据目录分离存放；字段内记录 `key_version` 以支持轮换。
- 用户口令派生（PBKDF2/Argon2）**不作为默认**：忘记口令即等于丢失所有 BMC 凭据。若提供，必须同时强制导出密钥备份。
- 硬性要求：BMC 密码永不进日志、永不进告警详情、导出资产时默认打码（需二次确认才含明文）。

### D10 IPMI 并发要防 BMC 过载（PRD 只写了「并发数可配」）

补三条约束：① **同一台 BMC 串行**，不并发；② 全局并发池按向导值；③ 单次超时（默认 30s）+ 连续失败 3 次进入指数退避（最长 30min），避免把 BMC 打挂后引发整机告警风暴。整机告警需与「采集失败」区分：采集失败只发 `agent_offline`/`collect_failed`，**不得**推导出「电源失效」。

### D11 硬件变更检测的去抖动

首次纳管会把所有部件当「新增」，需①首次采集仅建基线不产生变更事件；②`added/removed` 需**连续 2 次采集**一致才落库（防止 BMC 偶发少报一个 DIMM 就报变更）；③`modified` 只对白名单字段（序列号、容量、固件版本）敏感，避免热插拔噪声。

### D12 时序容量要算清楚再定保留期

单机约 60 条时间线，30s 采样 → 172,800 点/天 → 180 天约 3,100 万点，压缩后 **≈60MB/机**；300 台 × 180 天 ≈ 18GB。
因此结论是：**raw 30s 只保短期，长周期看聚合**。已落地的参数是 `retention.raw_days`（默认 7）与 `retention.agg_days`（向导可配，默认 180），聚合由进程内 rollup 生成 5m 序列（不再有 recording rule 这一层，见 D13）。

## 四、Native 化追加决策（D13–D17）

### D13 存储载体：SQLite 单文件 + 进程内嵌时序存储

- **元数据** → SQLite，纯 Go 驱动 `modernc.org/sqlite`（**必须免 CGO**，否则无法静态编译）。
- **时序** → `prometheus/prometheus/tsdb` 作为**库**嵌入进程，无独立进程、无端口、无容器。
- 后果：`manifest.platform` 不能再是 `all`（见 D16）；资源限制只能靠进程自限（见 D6）；时序查询不再经 Prometheus HTTP API，改为进程内 `Querier`。
- 完整 DDL 与存储参数见 `03-数据设计`。

### D14 零外部依赖是硬约束

不依赖容器运行时、不依赖外部数据库、不依赖目标机已装工具。
推论：① 不引入 `install_dep_apps`（如 `nodejs_v22`）；② Agent 自带 `smartctl`；③ 服务端 IPMI 优先纯 Go 实现，`ipmitool` 只作兜底。
收益：离线/内网部署不再受镜像仓库影响，常驻内存从 1.5–2GB 降到 120–250MB。

### D15 进程由 `cmd/main` 自管，不能用「容器托管」的思路

飞牛官方原生应用范式：`cmd/main` 自己 `start/stop/status`，用 **PID 文件 + `kill -TERM`（超时后 `kill -KILL`）**，日志写 `TRIM_PKGVAR`。
必须遵守的细节：`status` 返回 **0=运行中 / 3=未运行 / 1=失败**（错则应用面板状态错）；失败前把简洁的用户可见错误写 `TRIM_TEMP_LOGFILE`；`start` 必须幂等（升级脚本里被重复调用是正常路径）。
额外补一条：启动后做 `/healthz` 就绪探测（`curl` → `wget` → 退化为进程存活判定，飞牛上未必有 curl），避免「进程在但页面打不开」。

### D16 `platform` 必须按架构声明，ARM 要单独出包

官方规则：`platform=all` 仅当**包内不含特定架构二进制**时可用。本包内含 x86 原生二进制 → `platform=x86`。
后果：ARM 版飞牛设备需要同一份源码以 `GOARCH=arm64` 另出一个 `platform=arm` 的包，CI 必须做构建矩阵；`check_fpk.py` 已加断言，防止误写成 `all` 导致 ARM 设备装不上或装错。

### D17 前端走 `go:embed`，`app/ui` 只留桌面入口

前端构建产物（`web/dist`）编译进二进制，HTTP 层自行 gzip；`app/ui/config` 与 `app/ui/images` 仅承担飞牛桌面入口与图标。
好处：包内只有一个可执行文件，升级即替换二进制；代价是每改前端都要重新编译二进制，因此 CI 必须把「前端构建 → 嵌入 → 交叉编译 → 打包」串成一条命令。

## 五、技术栈与目录架构定案（D18–D21）

> 本节依据用户给出的《最终目录架构》定案，并已落到代码：`backend/`（Go）+ `frontend/`（Vue3）+ `agent/`（跨平台）+ `deploy/`（FPK 与构建脚本）。

### D18 存储可插拔：默认 SQLite，全部后端支持独立部署

- 抽象层：`internal/adapter` 定义 `MetadataStore` / `TimeSeriesStore` 两个接口 + 工厂注册表（`Register` / `Open`），
  后端实现放在子包（`adapter/sqlite`），由 `cmd/server` 以 `import _` 显式引入才注册 —— 上层业务代码对后端**零感知**。
- **默认 SQLite**（纯 Go 驱动 `modernc.org/sqlite`，免 CGO），零部署；
  MySQL / PostgreSQL / GBase8s / Prometheus / VictoriaMetrics / InfluxDB2 均按「独立部署」接入，
  通过 `db.dsn` / `timeseries.endpoint` 指向外部服务，凭据走环境变量。
- 可移植性代价（必须遵守，否则换库必踩）：
  1. 时间戳由**应用层**写入 UTC RFC3339 文本，不依赖各库的 `NOW()`；
  2. 不使用部分唯一索引（MySQL 不支持）——可空列唯一性用普通 `UNIQUE`（三方都允许多 NULL）；
     告警去重改用 `active_key`（firing 时写入、resolved 时置 NULL）；
  3. 枚举用 `TEXT + CHECK`，布尔用 `INTEGER 0/1`；
  4. 占位符差异由 `adapter.Rebind` 统一处理（sqlite `?` → postgres `$N`）。
- 后端可用状态通过 `GET /api/v1/system/storage/backends` 暴露给前端「存储管理」页，
  **明确区分「可用」与「规划中」**，避免用户切到未接通的驱动。

### D19 Web 框架定为 Gin（取代原「仅用标准库」的决定）

原计划用标准库 `net/http` 以减少依赖；用户定案为 Gin，已按此落地：
`api/web`（REST JSON）+ `api/agentpb`（Agent 通道）两组路由挂在同一个 `gin.Engine` 上，
中间件（请求 ID、访问日志、Recovery）与错误信封统一由 `pkg/utils` 提供，避免两个 HTTP 子包互相 import 成环。

### D20 Agent ↔ 服务端：HTTP/2 + TLS + Protobuf 二进制（与前端 JSON 通道严格隔离）

- 契约见 `backend/proto/agent.proto`（消息定义 + `AgentService`），代码生成走 `make pb`（`deploy/script/pb-gen.sh`）。
- 前端通道保持 RESTful JSON（+ WebSocket 推实时告警），**不复用 Agent 通道**，两者鉴权体系独立
  （前端会话 / Agent Bearer 令牌）。
- 当前实现状态：服务端与 Agent 均先以 **JSON 兼容通道**联调（协议字段与 proto 一一对应），
  proto 代码生成落地后只需替换 marshal/unmarshal 两处；服务端对 `application/x-protobuf` 请求返回
  **501 + 明确指引**，而不是把二进制当 JSON 解析后抛出难以定位的错误。
- 断网续传在 Agent 侧实现（spool 目录 + 24h 补传窗口，超窗数据本地丢弃）。

### D21 前端收敛为 TypeScript 工程，锁定 Node 22 / 24 双兼容

- 技术栈：Vue 3.5 + Composition API + **TypeScript** + Vite 8 + Pinia + vue-router + ECharts 6（按需引入）。
- `engines` 定为 **`">=22.12.0 <25"`**。
  注意：用户草稿里的 `">=22 <=24"` 在 semver 语义下会**排除 24.0.1 及以上版本**，属实际写错，已纠正。
- 路由用 **hash 模式**：飞牛桌面入口以 iframe 嵌入，hash 不依赖服务端 rewrite，刷新/深链不会 404。
- **实测结论（本机两条 Node 大版本各构建一次）**：Node 22.22.2 与 Node 24.21.0 均构建成功，
  且两次产物**字节级一致**（同一 asset 文件名与内容哈希）。
  踩到的坑：Vite 8 默认用 rolldown，`manualChunks` **只接受函数形式**，对象写法直接构建失败。

## 六、结论

- PRD 的**功能范围**没有结构性问题，模块划分可直接进入实施。
- 需要拍板的就是上面 12 条，其中 **D2（日志中心）、D4（RBAC 复用）、D3（自定义端口）** 三条是「PRD 写了但飞牛可能给不了」的，建议先按 P0 降级方案实现，真机验证后再决定是否补齐。

## D22–D30（2026-09-22 全量重设计新增）

### D22 gRPC 与 Web 共用单端口，按 Content-Type 分流

飞牛 `manifest` **只能声明一个 `service_port`**，Agent 无法走独立端口。
因此 gRPC 与 Gin 共用 18080：

```
Content-Type: application/grpc  → grpc.Server.ServeHTTP
其他                            → gin.Engine
```

判定条件：`r.ProtoMajor == 2 && strings.HasPrefix(contentType, "application/grpc")`。
代价是 HTTP/2 与 HTTP/1.1 共用监听器，TLS / h2c 配置必须一致。
**替代方案（未采纳）**：用 `cmux` 在连接层嗅探分流——多一个依赖，且 TLS 场景仍需 ALPN，收益不抵复杂度。

### D23 清单文件是无扩展名的 INI `manifest`，不是 `manifest.yml`

飞牛 FPK 的清单是 **key=value 的 INI 文件，且没有扩展名**。写成 `manifest.yml` 会让打包校验直接失败。
本仓库落地为 `deploy/fpk/metalwatch/manifest`，`check_fpk.py` 有断言防误写。

### D24 前端 engines 写 `">=22.12.0 <25"`，不能写 `">=22 <=24"`

`<=24` 语义上只到 24.0.0，会把 **24.0.1 及以上全部排除**，与「兼容 Node 24」的意图相反。
已在 Node 22.22.2 与 24.21.0 上分别完成构建与 `vue-tsc` 类型检查。

### D25 内嵌时序存储自研分块实现，不引入 `prometheus/prometheus/tsdb`

实测：`go get github.com/prometheus/prometheus/tsdb` 在本机**超过 12 分钟未完成**，
依赖树庞大（含大量间接依赖），与「零外部依赖、离线可装、单进程」的硬约束冲突。

改为**基于已有 SQLite 的分块压缩存储**：时间线目录表 + BLOB 块表，块内做 delta/XOR 压缩。
零新依赖、落盘事务可靠、备份与元数据统一。外部 Prometheus / VM / InfluxDB 仍按独立部署接入。

### D26 Windows 采集走 C# NativeAOT 组件 + `go:embed`

WMI 在 Go 里没有成熟的纯 Go 实现。方案：C# .NET 8 NativeAOT 编译为独立 exe，
`go:embed` 嵌入 Go 二进制，运行时释放到临时目录执行，目标机无需 .NET 运行时。
**风险**：本机无 .NET SDK，组件只交付源码与构建命令，出包前必须在一台装了 SDK 的机器上编译。

### D27 Mesh 采用服务端集中计算（Dijkstra），不做分布式路由

Agent 上报链路探测（`LinkProbe`），服务端基于全局拓扑算最优路径并下发路由表。
理由：集中式结果全局最优、便于审计与调参；分布式（如类 OSPF）在千节点规模下收益不明显，复杂度高得多。
降级：服务端不可达时 Agent 用最后一份路由表，仍不可达退化为直连 + 本地缓存。

### D28 BMC 指令由同网段 Agent 代执行

服务端通常**无法跨网段直连 BMC**（UDP/623），因此下发 `BmcCommand` 给同网段 Agent，
由它本地执行 IPMI 并回传 `BmcResult`。`command_id` 保证幂等，每次执行写审计日志。

### D29 proto 单一来源：Agent 复用 backend 的生成代码

Agent 未单独维护一份 proto 副本，而是通过 `replace` 指向 `../backend` 复用同一份生成代码，
避免两侧契约漂移。**若 replace 方案在交叉编译时出问题，退化为复制 proto 并本地生成，需同步更新本文。**

### D30 时序表独立于元数据方言目录

时序 DDL 放 `migrations/tsdb/` 而非 `migrations/sqlite/`：
元数据可切到外部 MySQL / PostgreSQL，时序仍保持内嵌，二者生命周期与迁移节奏不同，
混进方言目录会导致「元数据切走后时序表被漏建」。

## 五、结论

### D31 面向对象编码规范（2026-09-22 起，后续开发一律遵循）

> 目标：代码按「类型 + 行为 + 封装 + 依赖注入」组织，杜绝散装函数与全局容器传递。
> 本规范适用于 backend 与 agent 两个 Go module；前端遵循 Vue 组合式惯例，不套用本规范。

1. **领域概念一律成类型**：struct 承载数据，行为以方法挂在类型上。校验（`Validate`）、
   状态转换、格式转换（`DTO()` / `ToSamples()`）内聚在所属类型的**方法**里，
   不写「函数处理别人家数据」的散装逻辑。包级函数只允许两类：
   构造函数 `NewXxx`，以及与实例无关的纯工具（无状态、不改全局，如 `parseTime`）。
2. **构造函数完整初始化**：`NewXxx(依赖..., 选项...) (*Xxx, error)`。
   零值不可用的类型必须提供构造函数，在构造时完成不变量校验与默认值填充，
   禁止把半成品对象交给调用方再「补救式」初始化。
3. **封装**：跨包暴露的类型字段一律私有（小写），通过方法读写；
   需要对外提供的集合返回副本，防止调用方绕过方法改内部状态。
4. **依赖倒置 + 窄接口**：组件的依赖经**构造函数注入**，依赖的类型是接口。
   接口按消费方需要定义（Go 惯例：interface 定义在使用处），实现方零感知。
   禁止把整个 `app.Deps` 传进下层组件——那是 service locator 反模式；
   `app.Deps` 只在组合根（`cmd/*/main.go`、`NewRouter` 装配处）存在，
   由它拆出各组件真正需要的依赖。
5. **组合优于继承**：用嵌入与接口组合复用。Go 无继承，禁止用「基类 + override」模拟；
   领域对象不可比较继承深度，只问「谁拥有这个行为」。
6. **HTTP 层对象化**：每个路由域一个 Handler 结构体——
   `NewXxxHandler(依赖)` 构造 + `Register(rg)` 注册自己的路由 + 每条路由一个方法。
   路由表与处理逻辑同处一个类型；`func(d *Deps) gin.HandlerFunc` 闭包工厂**废弃**。
   Handler 只做三件事：解析参数、调服务/引擎方法、封响应；业务规则下沉到 service/engine。
7. **不可变值对象**：小而完整的概念（键、金额、坐标类）实现为不可变值对象
   （如 tsdb 的 `seriesKey`），全字段构造、无 setter、可比较。
8. **方法接收者**：有状态类型一律指针接收者；不可变值对象用值接收者。
   导出的方法需要文档注释说明「谁在什么时机调用它」。

> 落地证据：本轮已将 `api/web/handler`、`api/agentpb` 全部闭包工厂重构为
> Handler 结构体（见上第 6 条），`report.Loop` 重构为 `report.Reporter` 类型，
> `service.AlertService` 的规则装配收敛为不可变 `ruleSet` 值对象。
> 后续新增代码按本规范自查；评审时以上述条目为清单。

### D32 管理接口鉴权：会话令牌无状态 + 权限判定收口在中间件（2026-09-22）

**背景**：契约里只有一句「管理接口需要鉴权」，没定令牌形态与判定位置。W11 之前所有
`/api/v1/*` 裸奔（看板列为 🔴 阻断项）。

**决定**：

1. **令牌形态 = 自签 HMAC-SHA256**，不引入第三方 JWT 库，也不建会话表。
   密钥取既有的 `master.key`（0600，已用于 BMC 凭据加密），载荷含
   `uid/sub/role/exp`，默认 12h。
   *理由*：单机 FPK 场景没有集群会话共享需求；无状态省一张表和一次读库。
   *代价*：无法「强制下线」，登出只是客户端丢弃 —— 需要时再引入黑名单表。
2. **权限判定放中间件，不放 handler**：写操作（非 GET）一律要求 operator+；
   高危路径（用户 / Token / BMC 凭据 / 主机增删 / 明文导出）要求 admin，
   用 `method + 路由模板` 精确匹配。
   *理由*：**新增接口默认受保护**，不会因为某个 handler 漏写判断而裸奔。
   *代价*：新提高危路径必须手动加进 `adminOnly` 表（已在代码注释里标注）。
3. **开放接口令牌只存 SHA-256 摘要**，明文仅在创建响应出现一次（与 Agent 注册令牌同套做法）。
4. **口令用 Argon2id**（19 MiB / 2 轮，OWASP 下限档）—— 服务端可能跑在飞牛低端 ARM 上，
   64 MiB 档会让登录明显变慢。
5. **首次启动引导**：库里无账号时生成随机强口令管理员，打到日志并写入
   `bootstrap_admin.txt`（0600）。不开这个口子，新装环境所有接口 401，用户永远进不去。
6. **审计由中间件统一记录**写操作（ok/fail）与登录结果，handler 只补需要额外上下文的记录。

**反模式（已规避）**：不要写 `if MasterKey != nil { 启用鉴权 }` 这类兜底 ——
主密钥缺失时会话本就签不出来，与其静默放行造成裸奔，不如让登录直接失败暴露配置问题。

### D33 FPK 二进制内置 tzdata，构建脚本以 Python 为主入口（2026-09-22）

**背景**：W12 做「真机前自测」时用 `-trimpath` 交叉编译产物在本机实跑，进程启动即退出：
`配置校验未通过: server.timezone 无效: Asia/Shanghai`。同一份代码 `go test` 却全绿。

根因是时区数据的查找链：`time.LoadLocation` 依次查宿主机 `/usr/share/zoneinfo`、
`$GOROOT/lib/time/zoneinfo.zip`。前者在飞牛精简系统上不保证存在；后者被 `-trimpath`
抹掉了 GOROOT 路径。两边都落空 → 默认时区解析失败 → `Validate` 判为致命配置错误。

更糟的是 `Validate` 里那句注释写着「仅提示不阻断」，实际却把它 append 进了致命错误列表——
注释与行为不符，让这个坑在代码评审时更难被发现。

**决定**：

1. **`pkg/config` 空导入 `time/tzdata`**（约 450KB），时区数据与二进制一起分发。
   放在 config 而不是 `cmd/server`：是谁需要用，就由谁声明依赖，
   `Validate` 因此自洽，任何调用方（含测试）都不会再因环境差异拿到不同结果。
2. **无效时区名仍然阻断启动**，并修正注释。内置 tzdata 之后，解析失败只可能是名字写错，
   属于真实配置错误；静默回退 UTC 会让告警时间、报表口径整体偏移，比启动失败更难排查。
3. **构建与冒烟脚本以 Python 为主入口**：`deploy/script/build_fpk.py`（构建 + 版本回写 + 骨架校验 + fnpack）
   与 `deploy/tools/smoke_server.py`（拉起真实进程跑 10 项冒烟）。
   *理由*：`build.sh` 依赖 `dirname` / `node` / `npm` / `sed`，本机 Git Bash 的 PATH 损坏，
   这几个命令时有时无；Python 版只依赖标准库 + go。
   *配套*：`build.sh` 保留（Linux/macOS 正常环境可用），头部注明替代方案。
4. **构建产物不入库**：`.gitignore` 增加 `deploy/fpk/*/app/server/metalwatch[.exe]`
   （30MB 级静态二进制，之前未被忽略，差点进仓库）。

**验证方式（可复现）**：`python deploy/tools/smoke_server.py` 会以与
`cmd/main` **完全相同**的参数形态拉起真实进程，覆盖
启动就绪 → PID 文件 → 401 拦截 → 引导管理员 → 登录 → 带令牌访问 → 审计落库 →
**重启复用同一数据目录**（对应真机「重装/升级数据恢复」风险：旧令牌仍有效、管理员不重复生成）。
时区这类「只有真实产物才会暴露」的问题，正是靠它而不是单测发现的。

### D34 测试纪律：代码与对应测试同步交付（2026-09-25 起，强制）

> 背景：W1c–W18 的交付经验证明，Go 单测（进程内）与 Python 三层黑盒测试（进程间、
> 真实 HTTP/gRPC）互补——后者首轮运行即抓到 3 个 Go 测试盲区的真 bug
> （/alerts NULL hostname 全量 500、notify_state 回写失效、DTO 漏 json tag）。

**规则：编写代码后，必须编写对应的测试；未带测试的代码不合入。**

1. **三层覆盖要求**（按改动性质选择，评审时对照）：
   - **新增/修改 REST 端点** → `tests/python/unit/` 契约用例（正向 + 边界 + 输入验证 + 异常码），
     并在 `mw/endpoints.py` 登记端点（覆盖率报告会暴露遗漏）；
   - **跨模块协作链路**（上报→落库→告警→通知 等）→ `tests/python/integration/` 端到端用例；
   - **核心路径变更**（登录、健康探针、大盘等）→ `smoke/` 用例同步更新；
   - **bug 修复** → 先写复现用例（红）再修（绿），用例保留作回归守护；
   - **不要求**：纯重构（外部行为零变化）若现有用例全绿即可，无需为搬代码补测试。
2. **执行门禁**：
   - 本机：`cd tests/python && python run_tests.py`（全量 ~100s；冒烟秒级可高频跑）；
   - CI：`python-tests` job 在 Linux 上拉起服务端跑全量（离线判定用例无 Agent 自动跳过），
     与 go test / vet / race 同为合入门禁。
3. **测试数据隔离约定**（保证可重复执行）：
   - 主机名 / batch_id / 注册码 / 渠道名一律带 uuid 后缀；
   - **batch_id 尤其注意**：服务端按 batch 幂等去重，重放批次 202 + accepted=0 短路；
   - 时序查询默认区间 [now-1h, now]，测试上报不得使用未来时间戳的点。
4. **失败处理**：集成用例 timeout 先查服务端日志再怀疑用例；确认是服务端缺陷的，
   修复连同回归用例一起提交。

落地证据：`tests/python/`（冒烟 10 / 单元 45 / 集成 5，端点覆盖率 100%），
实测记录 §15。

### D35 全局环境变量区分开发/生产：`METALWATCH_ENV`（2026-09-26）

**背景**：服务端与 Agent 此前都没有「运行环境」概念，由此产生两个问题：

1. 服务端未指定 `--data` 时落到内置默认 `./data`：开发时仓库里凭空多出一个目录，
   生产时又可能写到不该写的位置（只读安装目录、或会被卸载清理的路径）。
   而"看起来无害的默认值"让这个问题一直没被发现。
2. Agent 的开发便利逻辑散在 `deploy/script/start-agent.ps1` 里——手工读 token 文件、
   host_id 缺失时兜底成 `"1"`、export 两个环境变量。换台机器、换个 shell（或直接
   `go run`）就失效，且 host_id 兜底成 1 是**静默连错主机**的隐患。

**决定**：

1. **单一全局变量 `METALWATCH_ENV`，取值只有 `dev` / `prod`**，两个 module 共用同一个
   常量与判定逻辑（`backend/pkg/env`，纯标准库；Agent 经既有 `replace` 复用 backend 的包，
   不引入新依赖）。
   解析优先级：**显式变量 > 存在 `TRIM_PKGVAR` 即判 prod > 默认 dev**。
   *理由*：FPK 真机必然注入 `TRIM_PKGVAR`，忘了写变量也不会掉进开发路径；
   而在源码目录里直接跑天然是 dev，无需任何前置设置。
   *代价*：非法取值直接报错而不静默回退——环境决定数据落在哪，猜错的代价
   （数据写错位置 / 丢失）高于启动失败。

2. **开发环境 = 各 main 处无参数直接可运行**：

   | 项 | 服务端 `cmd/server` | Agent `cmd/{windows,linux}` |
   | --- | --- | --- |
   | 配置 | 自动拾取 `configs/app.yaml`（缺失则用内置默认） | — |
   | 数据/spool | `tmp-data/` | `bin-local/spool` |
   | 监听 | `127.0.0.1:18080`（只听本机） | — |
   | 日志 | 同时输出到终端 | 输出到 stderr |
   | 凭据 | — | 自动读本地凭据，注册一次后无需任何环境变量 |
   | 提示 | 打印「环境/配置/数据/访问地址」横幅 | 启动日志带 `env=dev` |

   判定「用户是否显式传了 flag」用 `flag.Visit`，而不是比较 flag 默认值——
   后者会在默认值恰好等于环境默认值时误判。

3. **生产环境 = 只认显式注入**：服务端缺数据目录直接启动失败（取消 `./data` 兜底）；
   监听所有网卡（由飞牛网关转发）；Agent **不读**本地凭据文件，必须由 systemd
   EnvironmentFile / Windows 服务配置注入；FPK 的 `cmd/main` 显式 `export METALWATCH_ENV=prod`
   （显式声明而非只依赖兜底判定，排障时一眼可确认）。

4. **凭据来源收敛到一处**：新增 `agent/internal/agentcfg`（`ResolveSpoolDir` /
   `ResolveServer` / `ResolveIdentity` + 凭据 `Store`）。
   `report.NewReporter` 不再自己调 `HostIDFromEnv`，hostID 改为由调用方注入——
   否则开发环境从凭据文件读到的 host_id 传不进上报循环。
   凭据文件 `credentials.json`（0600，含 token + host_id + 上次注册的服务端地址），
   与既有 `token` 文件、`host_id.txt` 同目录（spool 的父目录），并**兼容读取旧布局**：
   已注册好的开发机不需要重新注册。
   同时 `report.Client.Enroll` 补返回 host_id（此前 JSON 通道把它丢了，
   导致两条通道「注册后能否无参数启动」行为不一致）。

**验证**：两个 module 的 `go test -count=1 ./...` 全绿（新增 `pkg/env`、`cmd/server`、
`internal/agentcfg` 三处用例）；实跑无参数 `go run ./cmd/server migrate` 输出
`env=dev data_dir=tmp-data`；无参数 serve 打印开发横幅且 2 秒内 `/healthz` 就绪。

### D36 D31 落地：类型化重构与同义实现收敛（2026-09-26）

**背景**：按 D31 巡检两个 module，找出两类反复出现的问题：

1. **散装函数处理别人家的数据**：`internal/service` 有 9 个包级 helper，
   其中 5 个（部件键、快照规范化、指纹、白名单取值、摘要）全在操作资产部件，
   却不属于任何类型——身份键与指纹的规则因此无法与「部件清单」这个概念一起被找到。
2. **同义实现各写一份**：指针↔值转换 4 份（`ptrString` / `optionalString` /
   `derefString` / `trimPtr`，前两者语义还不同）、字节截断 3 份
   （`notify.truncate` / `ipmipoll.truncateStr` / `report.trim`）、
   `agent` 两个 `main` 各写一套完整启动流程（其中 Linux 版在注册凭据写入失败时
   仍打印「凭据已写入本地」—— 两边行为已经真实分叉）。

**决定**：

1. **叶包约定**：通用小工具放**只依赖标准库**的叶包，且一个包一个主题：

   | 包 | 内容 | 为什么单独成包 |
   | --- | --- | --- |
   | `pkg/ptr` | `Deref` / `Of` / `OfNonEmpty` / `Trim` | 需要它的地方分处 `internal/notify` 与 `api/web/handler` |
   | `pkg/strs` | `OrDefault` / `JoinNonEmpty` / `Truncate` | `pkg/utils` 依赖 `internal/service`，工具放那里会形成 `service → utils → service` 的环 |
   | `pkg/timex` | `RFC3339` | 「时间戳一律 UTC RFC3339」是跨方言硬约束 ①，存储层与服务层各有一份实现 |

   **禁止**把通用工具塞进 `pkg/utils` —— 它是「带 HTTP 契约的工具包」，
   依赖 `internal/service`，不是叶包。需要被 service 层引用的工具一律新开叶包。
2. **领域概念成值对象（D31 第 1 条的具体化）**：一次快照规范化后的部件清单是
   `componentSet`，元素 `component` 包住存储行 `adapter.Component`。
   身份键 `key()`、摘要 `summary()`、白名单取值 `whitelistValue()` 挂 `component`；
   指纹 `fingerprint()`、留档 `payload()`、索引 `find()`/`add()` 挂 `componentSet`。
   原来 5 个自由函数全部删除。**「本轮采集的」与「库里既有的」都建成 `componentSet`**，
   两侧因此共用同一套键与比对规则，不会各算一套键而永远配不上。
3. **同义实现必须收敛成一个**，只搬位置不算收敛。本轮对照表：

   | 原 | 新 |
   | --- | --- |
   | `host.trimPtr` | `ptr.Trim` |
   | `host.defaultString` / `inventory.orDefault` | `strs.OrDefault`（保留裁剪语义） |
   | `enroll.optionalString` | `ptr.OfNonEmpty` |
   | `alerting.ptrString` / `inventory.ptrString` | `ptr.Of` |
   | `ipmipoll.derefString` | `ptr.Deref` |
   | `ipmipoll.truncateStr` / `notify.truncate` | `strs.Truncate` |
   | `inventory.strings_joinNonEmpty` | `strs.JoinNonEmpty` |
   | `adapter.defaultStr` | `strs.OrDefault` |
   | `inventory.marshalExtra` | `componentSet.add(row, extra)` 内部完成 |
   | `adapter.formatTime` / `service.formatUTC` | `pkg/timex` 的 `RFC3339`（adapter 保留内部名转发） |
   | `utils.atoiDefault` 手写十进制循环 | `strconv.Atoi` + 非负校验 |
   | 测试里手写的 `contains` / `indexOf` / `trimSpace` | `strings.Contains` / `Index` / `TrimSpace` |

   `Truncate` 顺带修正两处：`n <= 0` 不再 panic（旧实现 `s[:n]` 对负值会崩），
   且回退到最后一个完整 UTF-8 序列（截的多是中文错误信息，切半个字落库即乱码）。
   `agent/internal/report` 的 `trim` 是**截断补省略号**、与上面并非同一件事，
   保留在原地但改名为 `ellipsize`（原名会让人误以为是 `strings.TrimSpace`）。
4. **入口与中间件同样类型化**：`cmd/server` 拆为
   `options`（值对象，含 `flag.Visit` 判显式传入）/ `bootstrap`（成对申请-释放资源）/
   `command`（接口 + `serve`/`migrate`/`agent-code` 三个实现）/ `runtime`
   （build→listen→serve→close，close 幂等且 LIFO）；`api/web` 的鉴权中间件
   由包级 `Auth()` + 全局表改为 `Authenticator` 类型（`NewAuthenticator` + `Middleware()`）。
   Agent 两端 `main` 合并为共享 `agentapp.App`（`New(platform, version, opts)` +
   `Run(ctx)`），平台差异只剩 `CredentialHint()` 与 `Signals()` ——
   上面那处「Linux 谎报凭据已写入」的分叉由此在结构上不可能再发生。

**代价与边界**：`component` 是值接收者的只读包装，`adapter.Component` 仍是存储层的
数据载体，两者不合并——合并会让 service 的领域规则渗进 adapter。

**验证**：backend 全量、agent 全量 `go test -count=1` 全绿；`gofmt -s -l` 无输出、
`go vet` 退出 0；新增 `pkg/strs`、`pkg/ptr`、`pkg/timex` 用例，
分别钉住三条易漂移的边界：UTF-8 截断点、`Of` 与 `OfNonEmpty` 在空串上的差异、
「落库时间与宿主机时区无关」。

### D37 CI/CD：分平台流水线，且发布必须验证「制品本身」（2026-09-26）

**背景**：此前只有一条 `ci.yml`，而它里面有一条**从未真正跑通**的步骤——
全局 `CGO_ENABLED=0` 与 `go test -race` 互斥（race 检测器依赖 cgo），
本机实测 `go test -race` 在 `CGO_ENABLED=0` 下直接报 `-race requires cgo`。
「写进 workflow」与「真的跑过」是两件事，这是本轮最该记住的一条。
另一边，发布全靠手工，且看板里「仅出 x86 包」「fnpack 未安装」两条高优先级缺口一直挂着。

**决策**：

1. **两条流水线职责分离**：`ci.yml` 只做测试与编译验证，**不产出任何可发布物**；
   `release.yml` 按 tag 出包并发布。避免「CI 顺手出了个包」这种身份不清的产物。
2. **分平台一律用矩阵，且关闭 `fail-fast`**：服务端与 Agent 各出
   `linux/amd64`、`linux/arm64`、`windows/amd64`；FPK 按架构出 `x86` / `arm` 两个包。
   任一平台失败必须让整条链路失败，不允许「x86 过了就当过了」。
3. **`manifest.platform` 归构建脚本负责**：给 `build_fpk.py` 加 `--platform`，
   缺省按 `goarch` 推导（`amd64→x86`、`arm64→arm`），**推导不出来直接报错、不回落 x86**。
   架构标错的包会让设备装上跑不起来，比不出包更危险；而 `check_fpk.py` 只看
   「有没有原生二进制」，查不出这种错配。
4. **发布前验证的必须是「制品本身」**：给 `smoke_server.py` 加 `--binary`，
   release 流水线拿**下载回来的那份二进制**跑 10 项冒烟，而不是重新编译一份。
   两者未必等价——D33 的 tzdata 问题就是「单测全绿、真产物启动即死」的典型。
5. **命名与归集规则单独成脚本**：`deploy/tools/collect_release_assets.py` 持有
   产物命名表，并对「缺产物 / 目录为空 / 单目录多文件 / 名字不认识」四种形态直接报错。
   workflow 只负责上传下载。好处是这套规则**能在推 tag 之前本机跑一遍**
   （用假目录），而不是发完版才发现少了个 Agent 包。
6. **打包失败不许静默**：`build_fpk.py` 增加 `--require-fnpack`（缺 fnpack 即失败），
   并先清理旧 `.fpk` 再打包——否则上一轮的产物会被当成本轮产物上报
   （与 `run_tests.py` 清理 JUnit 旧文件同一类假绿来源）。

**代价与边界**：

- **前端产物目前没有消费者**：服务端既无 `go:embed` 也无静态路由
  （`NoRoute` 直接返回 404 JSON），所以**当前打出的 FPK 里 WebUI 不会生效**
  （桌面入口是指向 `:18080/` 的 iframe）。流水线如实打包现有内容——
  这是功能缺口，另立任务，不在本决策范围内。
- `deploy/` 暂不纳入 ruff 检查（尚有 21 条，多为 `BLE001` 盲兜底异常），
  先保住「能通过的基线」，不靠 `--select` 制造假绿。
- 真机三项验证（静态二进制运行 / `package` 用户写权限 / 重装数据恢复）仍只能上设备做。

**验证**：本机完成四组校验 —— ① workflow 用 Go 的 `yaml.v3` 真实解析
（本机无 PyYAML 且 pip 无网络，不自己手搓解析器，避免"接受非法 YAML"）；② matrix 键
覆盖检查；③ 全部 38 个 `run` 块的 `bash -n` 语法（先替换 `${{ }}` 表达式）；④
`release.yml` 上传的 artifact 名与归集脚本的期望做双向交叉比对（要求集合完全相等）。
这套校验当场抓出一个真 bug：`release.yml` 里 7 处分节标题漏写 `#`，
被 YAML 当成真映射键 → `unmapping key "meta" already defined`，整个文件解析失败。
另外实跑验证：`build_fpk.py` 的 `--platform` 四条路径（amd64→x86、arm64→arm、
显式覆盖、未知架构报错）与 `--require-fnpack` 守卫退出码；
`smoke_server.py --binary` 用真实 Windows 产物 10/10 通过、缺失二进制退出码 1；
`collect_release_assets.py` 五种形态用例（正常 + 缺目录 + 空目录 + 多文件 + 版本命名）。

### D38 WS 订阅登记必须先于协议握手（2026-09-26）

**背景**：D37 的流水线首次跑通后，`后端 · 质量门禁` 挂在**覆盖率**步骤：

```
--- FAIL: TestWebSocketAlertPush (5.07s)
    e2e_dataflow_test.go:384: 未收到 WS 推送: read tcp 127.0.0.1:49326->127.0.0.1:41039: i/o timeout
FAIL	github.com/LarryMKott/metalwatch/api/web	6.674s
```

同一步骤里的 `go test -race` 却是过的、本机也复现不出来。**先做了一次「重跑失败 job」
来定性**：同一 commit 重跑 13/13 全绿 → 偶发，不是 CI 专有的必现问题。
于是往「时序」而不是「环境」方向查，落在 `internal/ws/hub.go` 的 `serve`：

```go
conn, err := upgrader.Upgrade(...)   // ← 握手在这里就完成，客户端已收到 101
ch := h.subscribe()                  // ← 订阅登记在这之后
```

客户端一收到 `101` 就认为订阅已生效并开始发上报，而服务端此时可能还没把它放进
`clients`。`BroadcastJSON` 对空订阅集**不报错、只丢帧**（这是既定语义：慢消费者丢帧优于阻塞），
所以这一段窗口里的告警推送被静默吞掉，订阅者只能等到读超时。

**决策**：

1. **`serve` 里 `subscribe()` 前置于 `upgrader.Upgrade`**：让「Dial 返回」蕴含「已订阅」，
   窗口从根上消失。`Upgrade` 失败的分支显式 `unsubscribe`（避免漏掉订阅）。
   广播与退订之间的互斥由 Hub 既有的 `RWMutex` 保证，不会向已关闭通道写入。
2. **把这条不变式钉进回归测试**：`internal/ws` 新增
   `TestServeRegistersSubscriberBeforeHandshake`，走**真实 HTTP 升级路径**
   （gin 路由 + `httptest` + gorilla dialer），Dial 一返回就广播，200 轮必须次次收到，
   任一轮丢失即 fail-fast。不用「等一会儿再广播」的写法——那样就等于把要守的
   不变式从测试里删掉了。
3. **失败信息要能自我诊断**：e2e 用例在 WS 连上后先断言 `hub.ClientCount() == 1`，
   读超时的信息里带上当前订阅数。目的是把「订阅没登记」与「告警没触发」两类失败分开——
   否则两者都表现为同一个 5s 读超时，下次还会被带偏。

**代价与边界**：多了一次「握手失败要退订」的分支要维护。另外这个窗口本来就极窄
（服务端握手后几百纳秒内就入表），所以它一直是**低概率**事件——正因如此它才会
在功能开发期和本机反复跑测试时都躲过去，只在 CI 的调度下现形。

**验证**：① 量化旧顺序的丢失率——临时把顺序倒回去，300 次「Dial 返回即广播」丢 49 次（**16%**）；
② 回归测试在旧顺序下**第 1 轮**即失败，报错形态与 CI 那次同型（`read tcp …: i/o timeout`），
修复后 200 轮全过；③ backend 全量 `go test -count=1` 18 个包全绿，
`gofmt -s -l` 无输出、`go vet` 退出 0；④ 重跑 CI 的失败 job 13/13 全绿。
