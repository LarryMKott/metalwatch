# 05 开发计划（Native 版）

> **本次架构变更**：应用主体由「Docker 型 FPK（compose 编排 MySQL + Prometheus + API 三容器）」改为 **飞牛原生应用（native FPK）：单进程 Go 二进制 + 嵌入式存储**，不依赖容器运行时、不依赖外部数据库进程。
> 本文是开发计划的唯一入口；`01`~`04` 已按本计划同步修订。

---

## 0. 变更摘要

### 0.1 为什么要改（收益是量化的）

| 维度 | Docker 版 | Native 版 | 变化 |
| --- | --- | --- | --- |
| 依赖 | 需容器运行时 + 拉 3 个镜像 | 单二进制，**零外部依赖** | 离线/内网部署不再受镜像仓库影响 |
| 常驻内存基线 | 约 1.5–2 GB（MySQL 768M + Prom 512M + API 1G） | 约 **120–250 MB** | 4GB 内存机型的可行性从「勉强」变「宽裕」 |
| 包体积 | 数十 MB（仅 compose 与配置，镜像另拉） | 约 **30–60 MB** | 需注意 MMDB 与前端资源体积 |
| 首次启动 | 需拉镜像，分钟级 | **秒级** | |
| 故障面 | 容器 + compose + 三进程 | 一个进程 | 排障与升级逻辑大幅简化 |
| 代价 | — | 时序与元数据存储要自己扛 | 见 §1.3 选型与 §7 风险 R6/R7 |

### 0.2 被推翻的旧决策

| 旧编号 | 内容 | 处置 |
| --- | --- | --- |
| D1 部分 | compose bind `${TRIM_PKGVAR}` 持久化 | 保留结论（数据仍落 `TRIM_PKGVAR`），实现方式改为进程直写 |
| D6 | 用 compose 的 `cpus`/`mem_limit` 做资源限制 | **失效**。native 无配额声明机制，改为「进程自限」：GOMEMLIMIT + TSDB head 大小 + SQLite cache_size |
| D7 | MySQL vs SQLite「双路」 | **失效**。直接落 **SQLite**（纯 Go 驱动） |
| D3 | 单 `service_port` 分流 | **保留**，且 native 下更是唯一天然选择 |
| D12 | Prometheus 容量测算 | 结论保留，载体从 Prometheus 换成内嵌 TSDB |

## 1. 架构定型

### 1.1 进程与数据流

```
                     ┌──────────────────── 飞牛 OS（宿主机，无容器）────────────────────┐
                     │                                                              │
  巡检请求/浏览器 ───▶ │  metalwatch 进程（Go 静态二进制，以 package 用户运行）          │
                     │   ├─ HTTP 服务  :${TRIM_SERVICE_PORT}                        │
                     │   │    /                 → 内嵌前端（go:embed 的 Vue 构建产物）│
                     │   │    /api/v1/*         → 管理 API（会话鉴权）                │
                     │   │    /api/v1/agent/*   → Agent 上报（Token 鉴权）            │
                     │   │    /api/v1/open/*    → 开放只读 API（API Token）           │
                     │   │    /metrics          → Prometheus 文本格式（二期给 Grafana）│
                     │   ├─ 调度器（三档周期 + IPMI 任务池）                          │
                     │   ├─ 告警引擎（阈值判定 / 去重 / 抑制 / 通知）                  │
                     │   └─ 存储层                                                   │
                     │        ├─ SQLite  ${TRIM_PKGVAR}/data/metalwatch.db          │
                     │        └─ 内嵌 TSDB ${TRIM_PKGVAR}/data/tsdb/                │
                     └──────────────────────────────────────────────────────────────┘
                                        ▲ IPMI/UDP 623（带外，无 Agent）
                                        │
                    Linux Agent / Windows Agent ──TLS+Token──▶（跨平台，非 FPK，独立二进制）
```

### 1.3 技术选型

| 领域 | 选型 | 理由 / 备选 |
| --- | --- | --- |
| 服务端语言 | **Go 1.23+**，`CGO_ENABLED=0` 静态编译 | 单文件、无运行时依赖；与 Agent 共用一个 module，协议与 codec 复用 |
| HTTP | **标准库 `net/http`**（1.22+ 的 `ServeMux` 已支持 `"POST /api/v1/agent/report"` 模式） | 不引框架，减少升级面 |
| 元数据存储 | **SQLite + `modernc.org/sqlite`**（纯 Go） | 免 CGO 才能静态编译；备选 `zombiezen.com/go/sqlite` |
| 时序存储 | **`prometheus/prometheus/tsdb`（作为库嵌入）** | 成熟、纯 Go、Gorilla 压缩 ≈1.5–2 B/sample；备选 VictoriaMetrics `lib/storage`；**兜底**：自研定长块（仅当依赖体积/构建时间不可接受） |
| IPMI | **`github.com/bougou/go-ipmi`（纯 Go）** | 免装 ipmitool；**备选/兜底**：包内内置静态 `ipmitool`（musl 构建）。见风险 R1/R2 |
| SMART | 包内内置静态 `smartctl` + 直接读 `/sys`（NVMe） | smartmontools 无成熟 Go 替代；内置可避免目标机安装依赖 |
| Linux 采集 | `/proc`、`/sys`（sensors 走 hwmon 直读，**不依赖 lm-sensors 命令**）、`dmidecode`（Agent 以 root 运行） | 直读 hwmon 比解析 `sensors` 输出稳 |
| Windows 采集 | `github.com/yusufpapurcu/wmi` | 备选：Agent 内调 PowerShell CIM（Server Core 兜底） |
| 前端 | **Vue 3.5 + Vite + ECharts 6**（沿用既有习惯，不引入 Pinia / vue-router） | `vite build` 产物经 `go:embed` 进二进制 |
| 报表 | `excelize`（XLSX）；**PDF 后置**（中文字体内嵌 5–15MB，先不做） | 见风险 R5 |
| GeoIP | `oschwald/maxminddb-golang` + 随包 MMDB（Country + ASN） | 沿用 D8 |
| 邮件 | `net/smtp` + 自研模板 | |
| 数据库迁移 | 自研嵌入式迁移（`migrations/*.sql` + `schema_version` 表，`go:embed`） | 无 ORM，SQL 透明可审计 |
| 日志 | 结构化 jsonl + 按天/大小轮转，写 `TRIM_PKGVAR/logs/` | 替代原「飞牛日志中心」诉求（D2 结论不变） |
| CI | Gitee Go，构建矩阵：`linux/amd64`、`linux/arm64`（FPK）+ `linux/amd64|arm64`、`windows/amd64`（Agent） | |

**被否选项（记录理由，避免反复讨论）**

- ❌ MySQL / MariaDB：多一个进程、多一份内存，native 场景无收益。
- ❌ 外置 Prometheus：破坏「零依赖」前提。
- ❌ 直接调 `ipmitool` 二进制作为主线：多一个 glibc 依赖与解析成本（保留为兜底）。
- ❌ Python/Node 服务端：需要 `install_dep_apps` 拉运行时（如 `nodejs_v22`），与「零依赖、离线可用」目标冲突。
- ❌ ORM：表结构是本项目的核心资产，SQL 直写更利于审计与性能调优。

## 2. 容量与资源预算

时序写入速率 = 300 台 × 60 线 ÷ 30s = **600 点/秒**（峰值按 2 倍冗余 → 目标 ≥1500 点/秒）。

| 层 | 数据量 | 保留 | 估算占用 |
| --- | --- | --- | --- |
| 内嵌 TSDB（30s raw） | 51.8 M 点/天 | 7 天 | ≈ 0.7 GB |
| 内嵌 TSDB（5m rollup） | 5.18 M 点/天 | 365 天 | ≈ 3.8 GB |
| SQLite 元数据 | 部件 ≈ 50 行/机、变更/告警事件低频 | 长期 | < 500 MB / 年 |
| 前端 + MMDB + 二进制 | — | — | 30–60 MB |

内存预算（200 台规模）：Go 堆 ≈ 80–150 MB（含 TSDB head 与查询缓存）+ SQLite cache 64 MB，**GOMEMLIMIT=512MiB** 兜底，防止异常膨胀拖垮宿主机。

## 6. 关键路径与并行策略

```
关键路径： W0 → W1a(SQLite) → W3(协议冻结) → W4(IPMI)/W5(Linux Agent) → W7(告警) → P4
并行支线： W8(前端) 只依赖 W2+W3 的接口契约，可提前开工（先用 mock 数据）
          W1b(TSDB) 与 W2/W3 并行，但必须在 P2 前完成
          W9/W11 在 W7 定型后并行
```

- **单人开发**：严格按 `W0 → W1a → W3 → W5 → W4 → W1b → W2(补齐) → W7 → W8 → W9/W11 → W10 → W12` 推进。理由：协议先冻结，Agent 与服务端才能共用一套 codec；存储层只做能用最小子集，避免过早优化。
- **两人并行**：A 负责服务端（W0/W1/W2/W3/W4/W7/W11），B 负责客户端与前端（W5/W6/W8/W9）；**W3 协议必须先由 A 落成文档 + 桩服务**，B 才能开工。
- 硬性前置：**W10 的打包链路要在 P1 就跑通**，不要等到最后 —— 打包链路越早打通，后续每一步都能在真机验证。

## 7. 风险登记册

| # | 风险 | 影响 | 应对 |
| --- | --- | --- | --- |
| R1 | BMC 厂商 IPMI 实现差异大（Dell iDRAC / HPE iLO / 联想 XCC / 华为 iBMC / 超微） | 带外采集在某些机型读不到传感器 | 早期各型号一台做矩阵测试；保留 `ipmitool` 兜底通道；对读不到的项降级而不是报错 |
| R2 | 纯 Go IPMI 库成熟度 | 采集中断、协议兼容坑 | 先做 3 天 spike：能完成「建立会话 + 读 1 个传感器 + 读 SEL」即采用；不达标立即切内置静态 `ipmitool` |
| R3 | Windows WMI 在 Server Core / 精简镜像不可用 | Windows 采集失败 | Agent 内置 PowerShell CIM 兜底路径；两条路径都写好再发版 |
| R4 | 前端 + ECharts 体积 | 包体积膨胀、首屏慢 | ECharts 按需引入图表类型；构建产物 gzip 后目标 <800KB；资源走二进制内嵌由 HTTP 层做 gzip |
| R5 | PDF 中文字体需内嵌（5–15MB） | 包体积、许可证 | P4 只做 XLSX + HTML 报表；PDF 放二期，届时用子集化字体 |
| R6 | SQLite 单写者模型 + 高频写入 | 写阻塞、`database is locked` | WAL 模式 + 单一写队列串行化；元数据写入本就低频；`busy_timeout=5000` |
| R7 | TSDB 嵌入的写入吞吐与依赖体积 | 丢点、构建变慢 | 批量提交 + head block 调优；压测门槛 ≥1500 点/秒；若依赖不可接受则切自研最小 TSDB（已留接口） |
| R8 | `platform=x86` 后 ARM 设备装不了 | 覆盖面缺失 | CI 出 `arm` 包并分别提交；`check_fpk.py` 校验产物与 manifest 的架构一致性 |
| R9 | 本机 git 环境脆弱（历史事故：refs 被删、文件被真实删除） | 工作丢失 | 遵守项目约定：禁 `stash`/`checkout -b`；写操作前整包备份；提交前核对暂存区 |
| R10 | 飞牛侧未验证项集中（进程权限、PID 管理、共享目录、网关） | 后期返工 | **P1 里程碑内必须完成 V1–V3 真机验证**，不通过则暂缓 W4 之后的排期 |
