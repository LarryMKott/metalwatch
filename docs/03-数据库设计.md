# 03 数据库设计

两套存储各司其职，**不要互相兼职**：

- **MySQL 8.4** —— 会变的关系数据：资产、部件、变更、告警、用户、审计、任务。
- **Prometheus** —— 只追加的数值曲线：温度、转速、电压、功耗、SMART 数值、RAID 进度。

原则：**任何需要在 WebUI 里排序 / 筛选 / 关联 / 导出的东西进 MySQL；任何画曲线的东西进 Prometheus。** 告警阈值判定放在服务端内存中做（读 MySQL 阈值 + 读刚写入的采样值），不要让 PromQL 承担业务告警逻辑。

### 1.5 关键设计说明

- **`alert_event.active_key` 唯一索引**：MySQL 无部分唯一索引，用「firing 时写去重键、resolved 时置 NULL」实现「同一故障同时只开一条告警」，恢复后再触发会生成新事件，保留完整故障史。
- **`host_component` 的 `removed_at`**：不做物理删除，硬件「拔了又插」能识别为同一部件回归，而不是新增。
- **`collect_run` 增长最快**（每机每周期一行）。300 台 × 30s ≈ 86 万行/天。默认只保留 7 天，按 `started_at` 做 RANGE 分区或定时 `DELETE ... LIMIT`。
- **外键策略**：只有「强归属」关系用外键（部件/告警/令牌属于主机）。`collect_run.host_id` 故意不加外键，避免高频写入时锁竞争。
- **JSON 字段收敛**：`extra` / `detail` / `params` 是唯一的自由结构入口，禁止把可筛选字段塞进 JSON。

### 1.6 数据保留策略（默认值）

| 表 | 保留 | 说明 |
| --- | --- | --- |
| `collect_run` | 7 天 | 高频写入 |
| `hardware_snapshot` | 180 天，或仅保留 `fingerprint` 变化的那条 | 未变化时 payload 置 NULL |
| `alert_event` | 永久（resolved 后可按年归档） | 审计要求 |
| `change_event` | 永久 | 硬件变更史 |
| `audit_log` | 365 天 | |
| `report_job` 产物文件 | 30 天 | 数据库只留元数据 |

## 二、Prometheus 指标模型

### 2.1 命名与标签规范

- 指标名：`metalwatch_<domain>_<measure>_<unit>`，单位一律进名字（`_celsius` / `_rpm` / `_volts` / `_watts` / `_percent` / `_bytes`）。
- **公共标签**（每条时间线都带，用于筛选与聚合）：
  `host_id`、`host`（主机名）、`sn`、`site`、`rack`、`mode`（`agent` / `ipmi`）、`vendor`。
- **对象标签**（区分同一主机内的部件）：`slot`（`DIMM_A1`/`Disk0`/`PSU1`/`Fan3`）、`device`、`array`。
- **禁止**把序列号、告警文本、时间戳做成标签（高基数会打爆 TSDB）。序列号放 MySQL。

### 2.2 指标清单

| 指标名 | 类型 | 额外标签 | 说明 |
| --- | --- | --- | --- |

### 2.3 写入路径

```
Agent  ──JSON 上报──▶  API  ─┐
                             ├─▶ 服务端内存缓冲（按 host 聚合 30s）──▶ /internal/metrics  ◀── Prometheus scrape
IPMI 轮询（服务端自身）──────┘
```

- 服务端**不直接写 Prometheus**：避免把 TSDB 故障传导成采集故障。
- Agent 上报走自定义 JSON 协议（不是 Prometheus 格式），协议演进不受 TSDB 影响。
- Prometheus 只抓一个目标 `/internal/metrics`（见 `app/docker/prometheus/prometheus.yml`）。
- WebUI 出图统一经服务端转 `query_range`，不把 Prometheus 暴露给浏览器。

### 2.4 容量与保留

| 项 | 数值 |
| --- | --- |
| 单机时间线数量（估） | ≈ 60 条（含每盘 4 条 × 8 盘 = 32） |
| 30s 采样点数 | 2,880 点/天/线 → 172,800 点/天/机 |
| 压缩后占用 | ≈ 2 bytes/sample → **≈ 60MB/机/180天** |
| 300 台 × 180 天 | **≈ 18GB** |

**推荐默认**（替代「raw 直保 180 天」）：

- raw 30s → 保留 **30 天**；
- recording rule 生成 5m 聚合（`metalwatch:xxx:avg5m` / `:max5m`）→ 保留 **540 天**；
- WebUI 按查询区间自动选档：≤24h 用 raw，>24h 用 5m 聚合。

这比 PRD 里的单参数「保留时长」更省空间，也不牺牲短周期排障能力。
