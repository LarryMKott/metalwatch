### 8.3 过程中修掉的真 bug

1. **pipeline 停机丢点**：`Stop` 后的最终 flush 复用了已取消的 context，`BeginTx` 直接失败且错误被吞 —— 改为写入固定用独立 context。

3. **RAID 模板语义**：单 op 模板下 `ne` 对 crit 不成立，改为 `eq 1→major / eq 2→critical`（重建中不告警，进度走 `raid_rebuild_percent`）。

### 10.3 设计说明

- **上行时间轴**：流消息的 `timestamp` 为采集时刻（Unix ms），超 24h 补传窗口拒收——与 JSON 通道口径一致，为 W6 断网续传铺路。
- **下行命令通道**：`StreamServer.SendCommand(hostID, cmd)` 按主机注册下行 sink（断开即清理），W15 BMC 指令下发将直接复用；缓冲满返回 ResourceExhausted 而非阻塞。
- **优雅停机**：HTTP Shutdown → gRPC GracefulStop（GOAWAY，5s 超时硬停）。

- **登录守卫不持久化**：失败计数在进程内存，重启清零；跨实例部署需换成存储层计数。
- **权限判定在中间件**：写操作一律要求 operator+，高危路径（用户/Token/BMC 凭据/主机增删/明文导出）要求 admin。新增接口默认受保护，但**新路径若属高危需手动加入 `adminOnly` 表**。

- 前端令牌存 localStorage（XSS 可读），取舍理由：无富文本渲染入口 + 12h 过期，比每次刷新都要重登录更划算。

### 15.3 抓到的真 bug：`-trimpath` 二进制启动即死


| --- | --- | --- |

- `pkg/config` 空导入 `time/tzdata`（约 450KB），时区数据随二进制分发；放在 config 而非

- 修掉注释与行为不符：原文写「仅提示不阻断」，实际 append 进了致命错误列表。

**教训**：这类问题单测抓不到（`go test` 不吃 `-trimpath`），只有「按产物形态实跑」能抓到。

## 21. CI 偶发失败定位：WS 订阅登记晚于握手（2026-09-26）

**起因**：D37 的分平台流水线上线后，`run 36220229840` 里 13 个 job 有 1 个失败——
`后端 · 质量门禁` 的**覆盖率**步骤（不是历史那一步 `竞态检测`，race 这轮已首次跑通）：

```
--- FAIL: TestWebSocketAlertPush (5.07s)
    e2e_dataflow_test.go:384: 未收到 WS 推送: read tcp 127.0.0.1:49326->127.0.0.1:41039: i/o timeout
FAIL	github.com/LarryMKott/metalwatch/api/web	6.674s
```

**先定性，再定位**。本机复现不出来（受限调度 `GOMAXPROCS=1 -cpu=1` 单进程重复 20 次全绿、
按 CI 同款 `-coverpkg=./...` 参数跑也通过），于是先用 GitHub API **重跑失败 job**：
同一 commit 重跑 **13/13 全绿** → 判定为**偶发**。偶发就往时序方向查，不折腾环境。

**读数（关键的两行日志）**：

| 步骤 | `api/web` package 总时长 | 该用例 | 结论 |
| --- | --- | --- | --- |
| 竞态检测（`-race`） | 6.669s | 未打印（通过） | 同一步骤同一份代码能过 |
| 覆盖率（`-coverpkg`） | 6.674s | 5.07s 失败 | 失败点就是那个 5s 读超时 |

**根因**：`internal/ws/hub.go` 的 `serve` 里，订阅登记在握手**之后**：

```go
conn, err := upgrader.Upgrade(...)   // 握手在此完成，客户端已收到 101
ch := h.subscribe()                  // 订阅登记在这之后
```

客户端拿到 101 就认为订阅生效并立即发上报；服务端此刻可能还没把它放进 `clients`。
`BroadcastJSON` 对空订阅集**不报错、只丢帧**（既定语义），于是这段窗口里的告警推送
被静默吞掉，订阅者只能等到读超时——报错形态与上面那行一模一样。

**量化验证**（用真实 HTTP 升级路径写了一个 300 轮的最小实验，Dial 一返回就广播，不睡眠）：

| 顺序 | 结果 |
| --- | --- |
| 旧（先 Upgrade 后 subscribe） | **丢失 49/300（16%）**，单轮报 `read tcp …: i/o timeout` |
| 新（先 subscribe 后 Upgrade） | 200 轮全过 |

新写进 `internal/ws/hub_test.go` 的 `TestServeRegistersSubscriberBeforeHandshake`
就是上述实验的固化版（任一轮丢失即 fail-fast）。为确认它守的是对的点，把顺序**临时倒回去**
跑了一次：**第 1 轮**即失败，报错与 CI 那次同型。

**修复**：`subscribe()` 前置于 `upgrader.Upgrade`，`Upgrade` 失败的分支显式退订。
另把 e2e 用例的可诊断性补上——连上后先断言 `hub.ClientCount() == 1`，读超时信息里带上
订阅数，避免「订阅没登记」再次伪装成「告警没触发」。

**验证**：backend 全量 `go test -count=1 ./...` 18 个包全绿；`gofmt -s -l` 无输出、
`go vet` 退出 0；`internal/ws` 与 `api/web` 定点通过；CI 失败 job 重跑 13/13 全绿。

**记住这条**：本机能重复 20 次全绿的缺陷，不代表它不存在——它可能只需要换一套调度就现形。
下次拿到「偶发失败」，第一件事是用重跑把偶发与必现分开。

## 23. Agent 会话的两个并发缺陷：从 CI 偶发失败查到确定性复现（2026-09-26）

**触发**：CI run `36223226787`（提交 `cc27bcb`，**只改了一个 markdown 文件**）失败在
`Agent · 测试（vet / 单测）`：

```
--- FAIL: TestSessionReplayLiveAndCommand (2.05s)
    session_test.go:193: 等待超时: spool 清空
FAIL  github.com/LarryMKott/metalwatch/agent/internal/grpcstream  3.751s
```

**定性（把 D38 的套路原样再来一遍）**：

- 重跑失败 job → **13/13 全绿** → 偶发，不是必现；
- 本机 `-count=300` 全绿（40.8s）、`-cpu=1 -count=60` 也全绿（8.3s）→ 本地调度不出来；
- 提交只动 markdown → 与被测代码无关。
  **所以往时序查，不要往环境查。**

**日志里有个假信号**：`Agent` 那份日志第 194 行是
`echo "::error::以下文件未格式化："`，看着像 gofmt 失败。其实那是 runner 在回显
**脚本源码**（`##[group]Run unformatted=$(gofmt -s -l .)` 之后紧跟的那几行），
不是命令输出 —— 证据是它后面 `go vet`、`go test` 都照跑了（gofmt 真失败会被
`exit 1` 截断）。**读 Actions 日志要能区分「回显的脚本」与「脚本的输出」。**

**读代码定位**（本地既然调度不出来，就不该再靠运气复现）：两个缺陷见 D41 ——
补传与实时上报**并发写同一条 gRPC ClientStream**；以及落盘残留导致**延迟无上界**。

**确定性复现**：新增 `TestCollectOnceDrainsBacklogWhenConnected`，只考查
「一个采集周期」的行为（手工把 `s.st` 挂上真实流、手工调一次 `collectOnce`，
**不跑 `Run`**，不掺调度噪声）。**在修复前的代码上 2.22s 确定性失败**：

```
--- FAIL: TestCollectOnceDrainsBacklogWhenConnected (2.22s)
    session_test.go:291: 等待超时: 积压被本周期补发（spool 清空）
```

**这是本轮真正的收获**：同一个机制，在 CI 上是偶发（要等负载帮忙调度），
在本机是 0%（压根调度不出来）；把观测粒度从「整个会话生命周期」换成
「一个采集周期」之后，就变成 **100% 必现**。
**偶发不等于缺陷本身随机 —— 往往只是观测点的粒度太粗。**

> 一个自己踩的坑：第一版守卫测试在 `collectOnce` 返回后**立刻**断言服务端收到的批次，
> 得到 `实际 1 条: [backlog-1]`。那条实时报文其实发出去了，只是 fake 服务端是
> **异步 Recv**，还没读到。改成先 `waitFor(reportCount >= 2)` 再判顺序。
> **凡是对端异步，断言前必须先同步。**

**修复后**：守卫测试通过；`grpcstream` 全包通过；两条会话测试 `-count=150`
连跑 49s 全绿；agent 与 backend 全量 `go test -count=1 ./...` 通过；
`gofmt -s -l` 空；`go vet` 干净；`wfcheck` 全绿（39 个 `run` 块）。
CI 侧同时给 Agent 测试加了 `-race`（本机无 gcc 跑不了，只有 runner 能提供这个手段）。
