# 02 模块需求拆解与验收标准

把 PRD 的七章功能拆成 9 个可独立交付的模块，每个模块给出**交付物 / 验收标准 / 依赖**。
优先级：**P0 = 阶段 1-2 必须**，**P1 = 阶段 3-4**，**P2 = 阶段 5 或二期**。

> **2026-09-21 更新**：应用主体已改为**飞牛原生应用（无容器、单进程 + 嵌入式存储）**，
> 受影响的 M3（时序存储）、M7（曲线查询）、M9（打包）已同步修订；排期与工作分解见 `../03-计划/01-开发计划.md`。

---

## M1 资产台账（P0）

**交付物**：主机 CRUD、部件树、标签体系、资产导入导出（CSV/XLSX/JSON）、BMC 凭据加密存储。

**范围**
- 录入方式三选一：手工录入 / Agent 自动注册（enroll 后自动建 host）/ 批量导入（CSV 模板 + 校验报告）。
- 部件树按 `category` 分组展示：CPU、内存（按槽位）、磁盘、网卡、RAID 卡、电源、风扇、主板/BIOS/BMC 固件。
- GeoIP：收到上报 IP → MMDB 解析 → 写 `host.geo_*` + 自动打 `kind=geo` 标签。
- 导出：默认打码 BMC 密码与用户名；含明文导出需 `admin` 角色 + 二次确认 + 写审计。

**验收**
1. 导入 200 行 CSV（含 3 行故意错误的 SN/IP），返回逐行校验报告，正确行入库。
2. `bmc_credential.secret_cipher` 字段中搜不到明文；`detail`/`audit_log` 中不出现密码。
3. 同一 SN 二次导入不产生重复主机（按 SN + IP 提示合并/跳过）。
4. GeoIP 命中率：公网 IP 100% 有国家，私网 IP 不打地域标签（标记为 `内网`，不是 `未知国家`）。

**依赖**：无（M4 提供自动注册入口）。

## M2 采集调度引擎（P0）

**交付物**：定时任务框架（三档周期）、IPMI 任务池、容错与退避、采集执行记录。

**范围**
- 三档周期：静态资产 24h（可改）、传感器 10–600s（向导默认 30s）、SMART/RAID 5–30min。
- IPMI 任务池：全局并发可配；**同一 BMC 串行**；单次超时默认 30s；连续 3 次失败进入指数退避（上限 30min）。
- 单节点失败不阻塞全局；失败写 `collect_run` + 应用日志。
- 失败与告警解耦：采集失败只产生 `collect_failed`，**禁止**据此推导「电源失效/RAID 降级」等硬件结论。

**验收**
1. 300 台模拟节点、并发 16，单任务周期能被完整执行；人为让 10 台超时，其余 290 台结果不受影响。
2. 杀掉一个 BMC 的响应（模拟 hang），该主机进入退避，退避期间不再发起连接；恢复后 30min 内自动回到正常节奏。
3. 同一 BMC 的连接并发数观测值恒为 1。
4. `collect_run` 有完整 `state` 分布统计接口，7 天自动清理生效。

**依赖**：M1（主机与凭据）。

## M3 指标采集总线（P0）

**交付物**：Agent 上报接收、内存聚合缓冲、进程内嵌时序存储写入/查询、rollup 与保留策略。

**范围**
- Agent 上报 JSON → 校验 → 写内嵌 TSDB（经内存缓冲，批量提交）→ 同时做阈值判定（M6）。
- 幂等：`batch_id` 去重；允许**补传**（时间戳早于当前最多 24h），超出范围拒收并记 `collect_failed`。
- 缺样保护：某主机超过 `2 × sensor_interval` 未上报 → `metalwatch_up = 0` + `agent_offline` 告警。

**验收**
1. 30s 周期下，`metalwatch_up` 稳定为 1，曲线无断点；写入吞吐压测 ≥1500 样本/秒不丢点。
2. 同一 `batch_id` 重放 3 次，TSDB 样本数不增加。
3. 断开 Agent 60s，`metalwatch_up` 归零并产生一条 `agent_offline` 告警；恢复后告警自动 resolved。
4. 指标名/标签符合 `03-数据设计` §3 规范（写自动化用例校验指标白名单），且**不含高基数标签**。
5. raw 30s 与 5m 聚合两档在查询侧自动切换：≤24h 走 raw、>24h 走聚合，响应 `downsampled` 标注正确。

**依赖**：M2。

## M4 Agent 接入管理（P0）

**交付物**：注册码体系、Token 生命周期、在线状态、Agent 版本分布。

**范围**
- 一次性注册码（默认 1 次使用、24h 过期）→ enroll → 换取 per-host Token（只存哈希）。
- Token 吊销后，该 Agent 的上报立即 401；主机状态转为 `offline` 但资产保留。
- WebUI 展示：Agent 版本、最后心跳、上报成功率、待升级清单。

**验收**
1. 注册码二次使用被拒（401 `enroll_code_used`）。
2. 吊销 Token 后，Agent 下一周期上报收到 401 且不写任何指标。
3. 重装 Agent（Token 丢失）走「重新注册」流程，`host_id` 复用到同一台，不产生重复资产。

**依赖**：M1。

## M5 跨平台 Agent（P0）

**交付物**：Linux 静态二进制（systemd）、Windows 单文件 exe（注册为服务）、采集能力、断网续传。

**范围**
- Linux：`lshw`/`dmidecode`/`sensors`/`smartctl`/`storcli`/`megacli`（工具随包内置，不要求目标机安装）。
- Windows：WMI（`Win32_Processor`/`Win32_PhysicalMemory`/`Win32_DiskDrive`/`MSStorageDriver_FailurePredictStatus`）+ 厂商工具可选。
- 共用：Token 鉴权、TLS 上报、本地 spool 缓存（默认 24h / 上限 50MB，FIFO 丢弃最旧）、采集失败日志上报、静默升级参数（`--upgrade-url`）。
- 资源占用上限：空闲 CPU <1%、常驻内存 <50MB。

**验收**
1. Debian 12 / RHEL 9 / 飞牛 OS / Windows Server 2019+ 四类环境均能装、能起、能上报。
2. 拔网线 10min 后恢复：spool 中数据在恢复后 2 个周期内补传完成，WebUI 曲线补齐无空洞（超过 24h 的部分允许丢弃并标注）。
3. `smartctl` 在**未安装**该工具的目标机上也能正常采集 NVMe 温度（验证内置工具生效）。
4. 卸载脚本清理 systemd unit / Windows 服务，无残留。

**依赖**：M4 协议冻结。

## M6 告警引擎（P1）

**交付物**：阈值模板 + 单主机覆盖、分级、去重/抑制/维护窗口、Webhook/邮件通道、事件库。

**范围**
- 判定在服务端内存中做（不是 PromQL）；带 `duration_sec` 持续判定，抗瞬时抖动。
- 分级：`critical`（电源失效、RAID Failed、SMART 失效）/ `major`（RAID 降级、高温超阈值、风扇丢失）/ `info`（硬件变更、Agent 离线 5min 内）。
- 去重：靠 `alert_event.active_key` 唯一索引，同一故障同时只开一条。
- 抑制：`alert_silence` + `maintenance_window`；被抑制的事件**照常入库**，只是状态为 `suppressed` 且不通知。
- 恢复通知：`resolved` 时按需推送。

**验收**
1. 阈值 60℃/持续 120s：单次采样越界不告警；持续 130s 告警；恢复后 1 个周期内自动 resolved。
2. 主机级覆盖优先于模板：改单机阈值后，模板变更不再影响该机。
3. 维护窗口内 100 条告警全部入库且 `notify_state=skipped`，窗口结束后不补发。
4. Webhook 目标返回 500 时重试 3 次（指数退避），最终 `notify_state=failed` 并在 WebUI 可见失败原因。
5. 邮件正文不含 BMC 口令；Webhook payload 不含。

**依赖**：M3（数据）、M1（主机）。

## M7 WebUI（P1）

**交付物**：总览大盘、主机详情、故障大盘、检索、报表导出页、日志检索页。

**范围**
- 总览：服务器总数 / 在线 / 离线 / 告警数 / 按时序的告警趋势。
- 主机详情：资产卡片 + 传感器曲线（温度/转速/电压/功耗）+ SMART 表 + RAID 状态 + 变更历史。
- 故障大盘：按 `category` 聚合、故障主机清单、一键下钻。
- 检索：SN / 主机名 / IP / 标签 / 地域 组合过滤，支持保存筛选条件。
- 报表：资产清单、硬件巡检报告（JSON / XLSX / HTML），异步生成 + 下载。**PDF 放二期**（中文字体内嵌会让包体积增加 5–15MB，见 `05` 的 C3/R5）。
- 日志检索（替代原「飞牛日志中心」诉求，见 01 文档 D2）。
- 图表按中国习惯：**升温/异常用红、正常/降温用绿**。

**验收**
1. 300 台规模下总览首屏 <2s（服务端分页 + 预聚合）。
2. 主机详情页 24h 曲线一次加载 <1.5s（服务端按区间自动选 raw/聚合档，抽样步长自动）。
3. 巡检报告（XLSX/HTML）包含：硬件清单、期间告警、变更、传感器极值，中文不乱码；导出文件落到 `metalwatch/reports` 共享目录，用户可在文件管理器中直接取用。
4. 移动端浏览器（375px）可用：至少能看大盘与主机详情。

**依赖**：M1/M3/M6。

## M8 API 与集成（P1）

**交付物**：Agent 上报 API、管理 API、开放只读 API Token、出站 Webhook。

**范围与验收**：见 `02-接口契约.md`。其中：
1. 所有管理接口未登录返回 401，越权（viewer 调写接口）返回 403 且写审计。
2. 开放 API Token 只能读，尝试写操作返回 403。
3. `/api/v1/hosts/{id}/metrics` 返回的曲线与直接读内嵌 TSDB 的结果一致性抽查通过（含 raw 与 5m 两档）。

**依赖**：M1/M3/M6。

## M9 FPK 打包与运维（P2）

**交付物**：可安装 fpk（native 形态）、升级/回滚验证、持久化验证、x86 与 arm 双架构包。

**验收**
1. `fnpack build` 无警告产出 `metalwatch.fpk`；真机「手动安装」后进程被拉起（应用面板状态为「运行中」），桌面图标能打开 WebUI。
2. **持久化**：卸载（选择保留）→ 重装 → 资产与曲线完整恢复。
3. **升级**：0.1.0 → 0.2.0 走 `upgrade_callback` 迁移成功；元数据库有旧版本快照；失败时应用不可用但数据目录未被破坏。
4. **回滚**：用飞牛应用管理器的版本回滚能力退回上一版本，应用可正常启动。
5. 同一份源码分别产出 `platform=x86` 与 `platform=arm` 两个包（`GOARCH=amd64 / arm64`），各自在对应设备上安装可用。
6. **资源基线**：单进程常驻内存 ≤250MB（200 台规模），空载 CPU <1%；资源异常时不拖垮宿主机（`GOMEMLIMIT` 生效）。
7. **进程语义**：`start` 幂等（连调两次不出两个进程）；`stop` 先 TERM 后 KILL，无残留 PID 文件；`status` 三态返回码正确。

**依赖**：全部模块。

| 阶段 1 | M1 + M9 骨架 | fpk 能装能起，WebUI 能手工录入 3 台机器并看到资产卡片 |

| 阶段 4 | M6 + M8 + GeoIP 标签 + 报表 | 拔电源造真告警、Webhook 收到、完成一次巡检报告导出 |
| 阶段 5 | M9 全量 | 升级/回滚/卸载重装三条路径真机演练通过 |

## 建议的 P0 收口顺序

`M4 协议冻结 → M1 → M2 → M3 → M5(Linux) → M9 骨架补全`

理由：协议先冻结，Agent 与服务端才能并行开发；M9 不必等到最后——**打包链路越早打通，后面每一步都能在真机上验证**。
