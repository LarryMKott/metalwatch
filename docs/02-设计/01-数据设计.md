# 03 数据设计（Native 版：SQLite + 内嵌时序存储）

> **载体已变更**：原「MySQL 8.4 + 外置 Prometheus（容器）」改为 **SQLite 单文件 + 进程内嵌时序存储**。
> 数据模型语义、字段含义、指标命名规范**全部保留**，只换实现载体。
> 决策依据见 `../03-计划/01-开发计划.md`；本节所有 DDL 可直接落地为 `backend/migrations/sqlite/0001_init.sql`。

---

## 0. 两套存储的分工（原则不变）

- **SQLite（`data/metalwatch.db`）** —— 会变的关系数据：资产、部件、变更、告警、用户、审计、任务。
- **内嵌时序存储（`data/tsdb/`）** —— 只追加的数值曲线：温度、转速、电压、功耗、SMART 数值、RAID 进度。

铁律：**任何需要在 WebUI 里排序 / 筛选 / 关联 / 导出的东西进 SQLite；任何画曲线的东西进 TSDB。**
告警阈值判定放在服务端内存中做（读 SQLite 阈值 + 读刚写入的采样值），不要用查询语言承担业务告警逻辑。

## 1. SQLite 元数据库

### 1.1 连接与 PRAGMA（必须在每次连接时设置）

```sql
PRAGMA journal_mode = WAL;            -- 读写并发，单写者多读者
PRAGMA synchronous = NORMAL;          -- WAL 下兼顾安全与吞吐（非 FULL）
PRAGMA foreign_keys = ON;             -- SQLite 默认关闭，必须显式打开
PRAGMA busy_timeout = 5000;           -- 写锁等待 5s，避免瞬时 SQLITE_BUSY 报错
PRAGMA auto_vacuum = INCREMENTAL;     -- 定期回收，避免删除后文件不缩
PRAGMA cache_size = -65536;           -- 约 64MB 页缓存
PRAGMA mmap_size = 268435456;         -- 256MB 内存映射读
PRAGMA temp_store = MEMORY;
```

**并发模型**：SQLite 允许「多读者 + 单写者」。因此**所有写操作必须经过单一写队列串行化**（`internal/store` 内的 writer goroutine），禁止业务代码直接并发写。元数据写入本身低频（资产变更、告警、审计），不构成瓶颈。

### 1.2 DDL 类型与 MySQL 的对应规则

| MySQL 写法 | SQLite 写法 | 说明 |
| --- | --- | --- |
| `BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY` | `INTEGER PRIMARY KEY AUTOINCREMENT` | 只有 `INTEGER PRIMARY KEY` 是 rowid 别名 |
| `VARCHAR(n)` | `TEXT` | 长度约束用 `CHECK (length(x) <= n)` 按需加 |
| `ENUM('a','b')` | `TEXT` + `CHECK (x IN ('a','b'))` | 语义等价 |
| `SET('a','b')` | 拆成两个 `INTEGER` 标志位 | 见 `host.collect_agent/collect_ipmi` |
| `JSON` | `TEXT` + `CHECK (json_valid(x))` | 驱动侧用 `json_extract` 查询 |
| `DATETIME DEFAULT CURRENT_TIMESTAMP` | `TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now'))` | 统一 UTC ISO-8601 文本，可排序、可比大小 |
| `ON UPDATE CURRENT_TIMESTAMP` | **不支持** → 应用层写入时赋值 | 迁移器统一封装 `touch()` |
| `UNSIGNED` / `COMMENT=` | 去掉 / 用 `--` 注释 | |
| `KEY idx_x (...)` | 独立 `CREATE INDEX` | |
| 分区表 | 单表 + 定期清理（见 §1.5） | SQLite 无分区 |
| 部分唯一索引 | **`CREATE UNIQUE INDEX ... WHERE ...`** | SQLite 原生支持，比 MySQL 更省事 |

> `STRICT` 表（SQLite ≥ 3.37，`modernc.org/sqlite` 当前满足）用于强制类型检查，等价于 MySQL 的严格模式。若驱动版本不支持，去掉 `STRICT` 即可，其它不变。

### 1.4 关键设计说明

- **`uk_alert_active`（部分唯一索引）** 取代了 MySQL 时代的 `active_key` 置 NULL 技巧：`state='firing'` 时同一 `(host_id, category, metric, object)` 只能有一条。恢复后再触发会生成**新**事件，完整保留故障史。
- **`bmc_credential.secret_cipher` 用 `BLOB`**（不是 TEXT）：避免 base64 膨胀与编码歧义；AES-256-GCM 的 AAD 绑定 `host_id`，防止密文在主机之间搬运。
- **`host_component.removed_at`**：不做物理删除，硬盘「拔了又插」能识别为同一部件回归，而非新增。
- **外键策略**：强归属关系用外键（部件/告警/凭据属于主机）；`collect_run.host_id` 与 `audit_log.user_id` 故意不加，避免高频写入时的锁竞争。
- **`host.geo_country` 的 CHECK** 只做长度 2 的约束，私网 IP 不打地域标签（写 `NULL` 而不是写成 `XX`）。
- **JSON 字段收敛**：`extra` / `detail` / `params` / `config` 是唯一的自由结构入口，且都带 `json_valid` 约束；禁止把可筛选字段塞进 JSON。

### 1.5 保留与空间回收

| 表 | 保留 | 回收方式 |
| --- | --- | --- |
| `collect_run` | 7 天 | 每小时删除超期行（`DELETE ... WHERE started_at < ?`，分批 5000 行） |
| `hardware_snapshot` | 180 天，或仅保留指纹变化的那条 | 同上 |
| `alert_event` | 长期（resolved 后按年归档） | 手动导出后删除 |
| `change_event` / `audit_log` | 长期 / 365 天 | 同上 |
| `report_job` 产物文件 | 30 天 | 删除文件，保留元数据 |

**空间回收的必要条件**：SQLite 删除行不会自动缩小文件，必须周期执行 `PRAGMA incremental_vacuum;`（依赖 `auto_vacuum=INCREMENTAL`）。计划：每日 03:00 执行一次删除 + 增量回收，并在 WebUI「系统状态」中展示 `page_count × page_size` 与 `freelist_count`。

## 2. 内嵌时序存储

### 2.1 选型与目录

采用 `prometheus/prometheus/tsdb` 作为**进程内库**（无独立进程、无端口）。

```
data/tsdb/
├── wal/                预写日志（崩溃恢复）
├── chunks_head/        内存 head block 的落盘块
├── 01JXXXXXXX/         每 2 小时一个持久块（block），内含 index + chunks + meta.json
└── 01JYYYYYYY/
```

参数：`block 时长 2h`、`head 保留 3h`、`WAL 分段 128MB`、`retention.raw = 7d`。

### 2.2 写入路径

```
Agent（JSON 上报）─┐
                   ├─▶ 采集管道（解包 → 校验 → 归一化）─▶ 内存缓冲（按 host 聚合，30s 窗口）
IPMI 轮询（本进程）┘                                          │
                                                              ├─▶ TSDB Appender（批量 commit，每 5s 或满 5000 样本）
                                                              └─▶ 告警引擎（阈值判定，原始值）
```

要点：

- **Appender 批量提交**：逐样本 commit 会成为瓶颈；按批（5s 或 5000 样本）提交，压测门槛 ≥1500 样本/秒（300 台 × 60 线 ÷ 30s = 600 样本/秒，留 2 倍冗余）。
- **单写者**：TSDB 只允许一个 appender 串行提交，与 SQLite 写队列共用同一个 `internal/pipeline` 串行化通道。
- **幂等**：Agent 批次带 `batch_id`，重复批次在管道入口丢弃（内存 LRU 记录最近 10 万个 batch_id）。
- **乱序容忍**：TSDB 的 head 支持乱序写入，补传窗口 24h 内可直接写入。

### 2.3 查询

- 服务端直接调 TSDB `Querier`，MVP **不引入 PromQL 引擎**：只支持 `metric + label 匹配 + 时间区间 + step` 四种参数，足够覆盖所有出图需求，且避免引入 PromQL 的解析与兼容成本。
- 曲线查询：`≤24h → raw(30s)`；`>24h → 5m 聚合`。聚合档由服务端按区间自动选择，API 响应里通过 `downsampled` 标注。
- 越界点返回 `null` 而不是丢点，前端断线显示。

### 2.4 降采样（rollup）

- 每 5 分钟一次：把 raw 序列聚合为 `avg` 与 `max` 两个值，写成**独立序列**（命名加后缀 `_r5m_avg` / `_r5m_max`），而不是原序列的重复。
- 5m 序列的保留期由向导的 `wizard_metric_retention_days` 控制（默认 180 天）。
- **为什么不用 TSDB 原生多分辨率**：tsdb 不支持同一 series 的多分辨率存储，硬塞会导致选择器歧义；独立命名最直观，也便于将来导出给外部 Grafana。

### 2.5 容量与回收

| 层 | 数据量 | 保留 | 压缩后占用 |
| --- | --- | --- | --- |
| raw 30s | 51.8 M 样本/天（300 台） | 7 天 | ≈ 0.7 GB |
| 5m 聚合 | 5.18 M 样本/天 | 180 天（默认） | ≈ 1.9 GB |
| 5m 聚合（若选 365 天） | 5.18 M 样本/天 | 365 天 | ≈ 3.8 GB |

回收：TSDB 按 block 目录删除（`retention` 生效），比逐行删除高效得多；删除后调用 `db.CleanTombstones()`。仅在低峰期（03:00）执行。

## 3. 指标命名与标签规范（不变，Grafana 兼容）

- 指标名：`metalwatch_<domain>_<measure>_<unit>`，单位进名字（`_celsius` / `_rpm` / `_volts` / `_watts` / `_percent` / `_bytes`）。
- **公共标签**：`host_id`、`host`、`sn`、`site`、`rack`、`mode`（`agent`/`ipmi`）、`vendor`。
- **对象标签**：`slot`（`DIMM_A1`/`Disk0`/`PSU1`/`Fan3`）、`device`、`array`。
- **禁止高基数**：序列号、告警文本、时间戳不得作为标签（会打爆索引）。序列号放 SQLite。

| 指标名 | 类型 | 额外标签 |
| --- | --- | --- |
| `metalwatch_up` | gauge | — |
| `metalwatch_collect_duration_seconds` | gauge | — |
| `metalwatch_cpu_temp_celsius` | gauge | `chip` |
| `metalwatch_memory_temp_celsius` | gauge | `slot` |
| `metalwatch_fan_rpm` | gauge | `slot` |
| `metalwatch_voltage_volts` | gauge | `rail` |
| `metalwatch_power_watts` | gauge | `slot` |
| `metalwatch_psu_status` | gauge | `slot` |
| `metalwatch_disk_temp_celsius` | gauge | `device`, `model` |
| `metalwatch_disk_smart_status` | gauge | `device` |
| `metalwatch_disk_wear_percent` | gauge | `device` |
| `metalwatch_disk_reallocated_sectors` | gauge | `device` |
| `metalwatch_disk_power_on_hours` | gauge | `device` |
| `metalwatch_raid_state` | gauge | `array`, `controller` |
| `metalwatch_raid_rebuild_percent` | gauge | `array` |
| `metalwatch_nic_error_total` | counter | `device`, `type` |
| `metalwatch_host_info` | gauge=1 | `os_type`, `os_version`, `agent_version` |

取值约定：`smart_status` 0=OK / 1=预故障 / 2=失效；`raid_state` 0=Optimal / 1=Degraded / 2=Failed / 3=Rebuilding；`psu_status` 0=失效 / 1=正常。

**对外导出**：二期提供 `/metrics`（Prometheus 文本格式），把各序列最新值与 `up` 暴露出去，供外部 Grafana 抓取 —— 命名规范已按 Prometheus 惯例设计，因此这一步不需要改任何指标名。

## 4. 备份与恢复

| 对象 | 方式 | 时机 |
| --- | --- | --- |
| `metalwatch.db` | 应用内 `VACUUM INTO 'backup.db'`（在线一致快照，优于直接 copy） | 每日 03:30，保留 7 份 |
| `data/tsdb/` | 目录级复制（体积大，仅在用户显式操作时） | 手动触发 |
| 卸载保留 | 元数据库复制到 `metalwatch/backups` 共享目录 | `cmd/uninstall_init` |
| 升级前 | `metalwatch.db` 带旧版本号后缀的快照 | `cmd/upgrade_callback` |

恢复路径：停进程 → 用备份替换 `metalwatch.db` → 启动（迁移器会把版本对齐）→ 在 WebUI 校验资产数量。TSDB 丢失只影响历史曲线，不影响资产与告警，恢复优先级低。

## 5. 迁移策略

- 迁移器内嵌 `migrations/*.sql`（`go:embed`），按 `schema_version.version` 顺序执行，每个文件在**单个事务**内完成，`checksum` 防止已应用文件被改动。
- 升级流程：`cmd/upgrade_callback` → 停进程 → 快照 DB → `metalwatch migrate` → 启动。
- 破坏性变更（删列/改语义）必须分两次发布：先加新列并双写，下个版本再删旧列。
