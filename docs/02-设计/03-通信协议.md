# 03 · 通信协议设计

> 本文覆盖 Agent ↔ 服务端（gRPC）、Agent ↔ Agent（Mesh 中继）、服务端 → BMC（IPMI）、
> 服务端 → 前端（WebSocket）四条链路。REST JSON 接口见 [`02-接口契约.md`](02-接口契约.md)。

## 1. 通信矩阵

| 通信双方 | 协议 | 载体 | 用途 |
| --- | --- | --- | --- |
| 前端 → 服务端 | HTTPS + JSON | Gin | 业务接口、配置管理 |
| 服务端 → 前端 | WebSocket | Gorilla WebSocket | 实时告警推送、状态变更 |
| Agent → 服务端 | **gRPC 双向流 + Protobuf** | HTTP/2 + TLS | 指标上报、心跳、接收控制指令 |
| Agent ↔ Agent | gRPC + Protobuf | HTTP/2 + TLS | Mesh 数据转发、链路探测 |
| 服务端 → BMC | IPMI | UDP/623（经 Agent 代执行） | 带外采集、硬件控制 |

## 2. 单端口分流（关键约束）

飞牛 FPK 的 `manifest` **只声明一个 `service_port`**。因此 Agent 的 gRPC 与前端的
REST/WebSocket **共用 18080**，在 HTTP 层按 `Content-Type` 分流：

```
                ┌─ Content-Type: application/grpc ─→ grpc.Server.ServeHTTP
:18080 ─────────┤
                └─ 其他 ─────────────────────────→ gin.Engine
```

- gRPC 走 HTTP/2，路径形如 `/metalwatch.agent.AgentStreamService/Stream`；
- 前端 REST 走 `/api/v1/*`，WebSocket 走 `/ws/alerts`；
- 分流依据 `r.ProtoMajor == 2 && strings.HasPrefix(contentType, "application/grpc")`。

**代价与收益**：省去第二个端口（飞牛网络策略未必放行额外端口），代价是 HTTP/2 与 HTTP/1.1
共用监听器，需确保 TLS 与 h2c 配置一致。详见 [关键决策 D22](../01-架构/02-关键决策.md)。

## 3. gRPC 双向流

### 3.1 服务定义

```proto
service AgentStreamService {
  rpc Stream(stream AgentReport) returns (stream ServerCommand);
  rpc Enroll(EnrollRequest) returns (EnrollResponse);
}
```

`Stream` 承载全部实时交互；`Enroll` 为一次性 unary 调用（注册不需要长连接与保活）。

### 3.2 上行消息（`AgentReport`）

`kind` 字段区分消息类型，避免为每类数据各开一条连接：

| kind | 载荷 | 触发方式 |
| --- | --- | --- |
| `metrics` | `sensors[]` | 周期（默认 30s） |
| `asset` | `asset`（`AssetSnapshot`） | 周期（默认 1h）或服务端 `request_asset` |
| `heartbeat` | 无 | 周期（默认 30s，流空闲时保活） |
| `event` | `logs[]` | **事件触发**（温度突变、硬件故障），不受周期限制 |
| `link_probe` | `link_probes[]` | 周期，Mesh 拓扑探测结果 |
| （回执） | `bmc_results[]` | BMC 指令执行完成后回传 |

- `batch_id` 为幂等键：断网续传重放同一批数据时，服务端据此去重。
- `timestamp` 为**采集时刻**（Unix 毫秒），不是上报时刻——补传场景必须区分二者。

### 3.3 下行消息（`ServerCommand`）

| 字段 | 用途 |
| --- | --- |
| `bmc_cmd` | BMC 控制指令（风扇 / 电源 / 指示灯） |
| `config` | `AgentConfig` 热更新，Agent 不重启生效 |
| `route_table` | Mesh 路由表下发 |
| `request_asset` | 立即触发一次全量资产采集 |
| `server_time` | RFC3339 UTC，供 Agent 校正时间偏差 |

### 3.4 连接生命周期

1. **建连**：TLS + Token（`authorization: Bearer mwa_...`）；
2. **保活**：gRPC Keepalive（服务端 `Time=60s`、`Timeout=20s`，允许无调用保活）；
3. **重连**：客户端指数退避（1s → 2s → 4s … 上限 60s）+ 随机抖动，避免重连风暴；
4. **断网**：采集数据转写本地 bbolt 队列，重连后按序补传；
5. **服务端优雅停止**：先发 `GOAWAY`，等待在途消息落盘后再关闭。

## 4. Mesh 最优路径机制

解决跨网段、出口带宽受限场景下 Agent 无法直连服务端的问题。

```
   [Agent A] ──直连──> [服务端]
       │                  ▲
       └──中继──> [Agent B] ┘      ← B 与服务端同网段，A 借道 B
```

### 4.1 流程

1. **拓扑收集**：各 Agent 定时探测邻节点（`LinkProbe`：`rtt_ms` / `loss_rate` / `direct`），随流上报；
2. **集中计算**：服务端 Mesh 引擎基于全局拓扑运行 **Dijkstra**，权重
   `cost = rtt_ms + loss_penalty×loss_rate×1000 + hop_factor×hop_count`；
3. **路由下发**：计算结果以 `RouteTable`（带单调递增 `version`）经 gRPC 流下发到所有 Agent；
4. **转发执行**：Agent 按路由表转发数据，`MeshHeader` 携带 `hop_count` 与 `path`：
   - 转发前检查自身是否已在 `path` 中 → 丢弃（防环路）；
   - `hop_count` 超过 `max_hops` → 丢弃，改走直连或缓存；
5. **降级策略**：服务端不可达时，Agent 用本地缓存的最后一份路由表；仍不可达则退化为直连，
   失败则写入 bbolt 等待恢复。

### 4.2 消息分级

`MeshHeader.priority`：`1`=紧急（温度突变 / 硬件故障）优先转发，`2`=普通（周期指标）批量合并。
紧急消息不参与批量合并，立即推送。

## 5. BMC 管控链路

服务端通常**无法跨网段直连 BMC**，因此控制指令由同网段的 Agent 代执行：

```
服务端 ──gRPC 下行 BmcCommand──> Agent ──IPMI(本地)──> BMC
服务端 <──gRPC 上行 BmcResult──── Agent <────────────── 
```

- `command_id` 作为幂等键，重复下发只执行一次；
- 每次执行写**审计日志**（操作人、目标、指令、结果、时间）；
- `BmcCapability` 由 Agent 注册时上报，前端据此决定是否显示对应操作按钮；
- 自动闭环：控制引擎按温度阈值自动下发 `fan_speed`，`auto_mode=true` 可交还 BMC 自动控制。

## 6. 断网续传

| 环节 | 策略 |
| --- | --- |
| 缓存介质 | bbolt 本地队列（`<data>/spool.db`），按序写入 |
| 补传窗口 | `spool_max_hours`（默认 24h），超时丢弃并记日志 |
| 去重 | 服务端按 `batch_id` 去重（表 `ts_ingest_dedup`） |
| 时间戳 | 上报用**采集时刻** `timestamp`，补传不改变时间轴 |
| 容量保护 | 队列达上限时丢弃最旧的普通消息，保留紧急消息 |

## 7. 前端 WebSocket

- 端点 `/ws/alerts`，与 REST 共用 18080；
- 推送内容：告警新增 / 恢复、主机上线 / 离线、BMC 指令结果；
- 客户端指数退避重连；**生产环境默认关闭**（`.env.production` 的 `VITE_WS_ENABLED=false`），
  待 W7 告警链路交付后再开启。
